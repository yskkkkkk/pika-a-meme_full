퀴즈가 자꾸 낯익었습니다

요즘은 기능을 더 붙이는 대신 코드를 한 줄씩 다시 읽고 있습니다.

자바만 쓰던 사람이 굳이 코틀린으로 백엔드를 짠 건, 어차피 배울 거 제대로 배워보자는 마음이었거든요. 그래서 요즘은 AI한테 1:1 과외를 받습니다. 개념을 설명해주고, 중간중간 퀴즈를 내주거든요.

그런데 어느 순간부터 퀴즈에 딸려 나오는 예시 코드가 자꾸 낯이 익더라고요. "이거... 혹시 제 코드 아닌가?" 하는 생각이 들었거든요.

한 번도 아니고 세 번이었습니다.

val 하나만 var이었던 자리

첫 과외 주제는 코틀린의 val과 var였습니다. 자바의 final 필드와 일반 필드 차이라고 생각하면 쉽거든요. val은 게터만, var는 게터와 세터가 같이 생기고요.

설명에 딸려 나온 예시가 제 User 클래스였어요.

// pam-domain — User.kt class User( val id: UUID, val username: String, val email: String, val createdAt: LocalDateTime, var updatedAt: LocalDateTime // 혼자만 var )

모든 필드가 val인데 updatedAt 하나만 var였습니다. "혼자 var인 거 보이시죠?"라는 설명이 따라왔고요.

듣다가 제가 되물었어요. "근데 updatedAt은 다른 값이 바뀔 때 같이 따라 바뀌는 종속값 아닌가요?"

비밀번호가 바뀌든 주소가 바뀌든, 그 변경에 딸려서 갱신되는 값이거든요. 그런데 정작 그 '바뀌는 값'들은 전부 val이라 바뀔 일이 없었습니다. 바뀔 일 없는 객체에 수정 시각만 혼자 열려 있던 셈이죠.

결국 updatedAt은 도메인에서 들어냈어요. 수정 시각은 비즈니스 규칙이 아니라 DB가 기록하는 값이니까, 그쪽(@UpdateTimestamp)에 맡기는 게 맞더라고요.

문법 하나 배우려고 들여다본 한 줄이 설계 질문으로 번지는 건, 생각보다 자주 일어나더라고요.

락을 걸었는데 왜 소용이 없었을까

예전에 하트 시스템 글에서 하트에 분산 락을 걸었다고 썼거든요. 하트가 동시에 두 번 차감되는 걸 막으려고요. 그땐 그걸로 끝난 줄 알았습니다.

그 코드를 에이전트가 다시 예시로 가져왔어요. 이번 주제는 스프링의 @Transactional이었고요.

@Transactional // 1) 트랜잭션은 메서드 바깥에서 열리고 fun consumeHeart(userId: UUID, heartType: HeartType) { lockManager.withLock("lock:heart:$userId") { // 2) 락은 안쪽에서 잡힌다 // 하트 차감 로직... heartRepository.save(heart) } // 3) 락 해제 — 그런데 트랜잭션은 아직 커밋 전 } // 4) 여기서야 커밋

퀴즈가 따라왔어요. "스레드 A가 락을 얻고 로직을 마친 뒤 락을 반납했습니다. 바로 그 직후 스레드 B가 같은 유저 ID로 락을 얻으면, B는 A가 바꾼 하트 개수를 정상적으로 조회할 수 있을까요?"

저는 이렇게 답했습니다. "비정상 조회가 가능할 것 같습니다. 락을 얻는 시점이 차감이 끝나기 전이라, 락 시점을 HeartService에 들어가기 전으로 당겨야 하지 않나..." 방향은 맞았는데, 진짜 원인은 조금 더 안쪽에 있었어요.

@Transactional은 AOP 프록시로 동작하거든요. 메서드에 들어갈 때 트랜잭션을 열고, 메서드를 빠져나온 뒤에 커밋합니다. 그런데 락은 메서드 안쪽 withLock 블록에서 잡고 풀려요. 순서를 늘어놓으면 이렇게 됩니다.

① 스레드 A — 락 획득

consumeHeart에 진입해 락을 잡고 하트를 차감합니다.

② 스레드 A — 락 해제

withLock 블록을 빠져나오며 락을 반납합니다. 그런데 트랜잭션은 아직 커밋되지 않았거든요.

③ 스레드 B — 마의 구간

바로 이 틈에 B가 같은 락을 얻습니다. A가 차감한 결과가 DB에 반영되기 전이라, B는 옛날 하트 개수를 읽고요.

④ 결과 — Lost Update

A와 B가 같은 값을 기준으로 각자 차감합니다. 하트 하나는 두 번 쓰였는데, 장부엔 한 번만 빠지고요.

락은 분명 풀렸는데 트랜잭션은 아직 커밋 전인 구간이 생기거든요. 락을 거는 것까진 맞았지만, 그 락이 트랜잭션보다 안쪽에 있으면 없는 거나 마찬가지였어요.

"이거 혹시 제 코드에도 있나요?" 물었더니, 역시 있었습니다.

수정은 락이 트랜잭션을 통째로 감싸도록 바꾸는 방향이었어요. @Transactional 어노테이션을 떼고, 락 블록 안에서 TransactionTemplate으로 트랜잭션을 직접 열고 닫았거든요. 그래야 '락 획득 → 트랜잭션 시작 → 커밋 → 락 해제' 순서가 보장되고요.

면접 단골 문제라는 말이 괜히 나온 게 아니더라고요. 락만 걸면 끝이라고 믿었는데, 정작 그 락이 트랜잭션 안쪽에 갇혀 있었거든요.

틀린 문제, 그리고 회사 코드

세 번째 퀴즈는 솔직히 틀렸습니다.

이번엔 Rate Limit 코드였어요. 요청 수를 INCR로 올리고, 키가 처음 생겼을 때만 EXPIRE로 만료 시간을 거는 코드였거든요.

private fun consume(key: String, window: Duration): Long { val count = redisTemplate.opsForValue().increment(key) ?: 1L // 1) INCR if (count == 1L) { redisTemplate.expire(key, window) // 2) 그 다음 줄에서 EXPIRE } return count }

에이전트가 물었어요. "이 코드, 원자성이 보장될까요?" 저는 별 문제를 못 느꼈습니다. 그게 틀린 답이었고요.

문제는 INCR과 EXPIRE가 두 줄로 떨어져 있다는 데 있었거든요. 두 가지 상황에서 깨졌어요.

하나는 서버가 죽는 경우입니다. INCR로 키를 만든 직후, EXPIRE를 부르기 전에 서버가 내려가면 만료 시간 없는 키가 영원히 남거든요. 메모리를 점유하는 좀비 키가 되고요.

다른 하나는 동시 요청입니다. 거의 같은 순간에 요청 둘이 들어오면, A가 EXPIRE를 부르기 전에 B가 INCR로 값을 2로 만들어요. 그러면 B는 count == 1 조건을 못 타서 그냥 지나가고, A의 EXPIRE가 어쩌다 누락되면 이 키도 만료 없이 남고요.

설명을 듣고 나서야 "아, 이건 고쳐야겠다" 싶더라고요. 수정은 INCR과 EXPIRE를 Lua 스크립트 하나로 묶는 거였어요. Redis가 스크립트를 통째로 원자적으로 실행하니까, 두 명령 사이에 끼어들 틈이 사라지거든요.

그런데 이 글을 쓰면서 켕기는 게 하나 있었습니다. 회사 운영 코드에도 비슷한 모양이 있거든요.

다행히 매일 한 번 남은 키를 정리하는 배치가 돌고 있어서 아직 사고는 없었어요. 그래도 토이 프로젝트에서 배운 걸 회사 코드에 적용할 일이 생긴 거죠. 조만간 손볼 생각입니다...

이번에 다시 챙긴 것

예전엔 AI한테 "이슈 좀 찾아줘"라고 통째로 던졌거든요. 그렇게 찾은 것도 있긴 했는데, 어딘가 겉도는 느낌이었어요. 이번 세 개는 버그를 찾으려다 찾은 게 아니라, 문법 하나 동작 하나 배우겠다고 코드를 한 줄씩 짚다가 걸린 거였고요. 그렇게 걸린 게 훨씬 깊고 정확하더라고요.
