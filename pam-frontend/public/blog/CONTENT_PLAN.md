## 0. 전체 내러티브 (Narrative Arc)

블로그 전체는 **"Pet-Pass의 실패에서 출발 → 피카밈에서 의식적으로 다르게 한 결정들 → 그 결정이 만든 사건들 → 회고"** 라는 일관된 흐름을 가진다.

```
[시작]  Pet-Pass 회고 → 피카밈의 3대 원칙
   ↓
[설계]  Clean Architecture, 하트 분리, R2 미저장 결정
   ↓
[사건]  로그아웃 안 됨, OAuth2 깨짐, 미션 접점 버그
   ↓
[운영]  Rate Limit, 캐시 전략, Cloudflare 최적화
   ↓
[확장]  i18n 풀스택, 폰트 랜덤화 같은 후반부 결정
   ↓
[회고]  1개월간 배운 것, AI 협업의 현실
```

각 글은 **"문제 → 시도 → 해결 → 배운 것"** 4단 구조를 공유해 독자가 패턴을 학습하게 한다 (post1~3이 이미 이 구조).

### 📄 post4 — "로그아웃이 5번 깨졌다 — 쿠키 정책과의 싸움"

**카테고리:** 피카밈 개발기 · 이슈 #3
**가제 후보:**
- 로그아웃이 5번 깨졌다 — 쿠키 정책과의 싸움
- "로그아웃 됐다"가 거짓말이었던 1주일
- HttpOnly Cookie를 지운다는 것

**한 줄 메시지:** "쿠키는 '심으면 사라지는 것'이 아니라 '발급한 호스트에서만 지울 수 있는 것'이다."

**왜 이 글이 강력한가:** 5차에 걸친 디버깅 기록 그 자체가 "근거 기반 사고"를 보여주는 가장 좋은 증거. 면접에서 "최근 어려웠던 버그는?" 질문에 이 글 하나 던지면 끝.

**도입부 훅 (그대로 써도 됨):**
> 로그아웃 버튼을 누르면 토스트가 뜬다. "로그아웃 되었습니다." 새로고침하면 다시 로그인 상태다. 1차에서 멈췄으면 좋았겠지만, 결국 5차까지 갔다.

**섹션 구조:**
1. **현상** — 로그아웃 후 새로고침하면 로그인 상태로 돌아옴
2. **1차 진단: React Query 캐시일 거다** → 캐시 지워도 동일. (실패)
3. **2차 진단: 크로스 오리진 fetch는 Set-Cookie를 적용 안 한다** → 클라이언트가 받는데 적용 안 함. (부분 원인)
4. **3차 시도: `window.location.href`로 네비게이션** → 로컬은 됨, 운영은 안 됨. (?)
5. **4차 발견: domain 속성이 다른 쿠키는 별개다** → 배포 전 쿠키와 배포 후 쿠키가 공존
6. **5차 최종: host-only 쿠키는 발급한 호스트에서만 지울 수 있다**
   - 프론트는 `pick-a-me.me`, 백엔드는 `api.pick-a-me.me`
   - 쿠키는 백엔드 호스트가 발급 → 프론트는 못 지움 → 백엔드로 GET 네비게이션해서 거기서 Set-Cookie로 지워야 함
7. **부가 발견: JSESSIONID가 살아 있어서 JWT 삭제 후에도 재인증되더라** → Spring `SessionCreationPolicy.STATELESS` 전환

**비주얼 컴포넌트 추천:**
- 타임라인 (`.timeline`) — 1차~5차 시도 색으로 구분 (실패는 `.fail`)
- 코드 블록 — Set-Cookie 헤더 예시 (`Max-Age=0; Path=/; Domain=...`)
- 흐름 박스 — "프론트 → /api/auth-logout (백엔드 호스트) → Set-Cookie 삭제 → 리다이렉트" 3단계

**lesson-box (한 줄):**
> 보안 기능은 정상 동작할 때보다 비정상 상황에서 그 모양이 드러난다. 쿠키, 세션, 토큰은 "넣고 빼는 변수"가 아니라 "정책으로 격리된 자원"이다.

**다음 글 연결:** "쿠키 지우기는 끝났지만, OAuth2는 또 다른 곳에서 깨졌다 → post6"

### 📄 post5 — "모든 밈을 R2에 저장하지 않기로 한 이유"

**카테고리:** 피카밈 개발기 · 기획 & 설계 #1
**가제 후보:**
- 모든 밈을 R2에 저장하지 않기로 한 이유
- 처음 설계를 뒤집은 이야기
- 저장 비용이 발생하는 시점을 늦추는 방법

**한 줄 메시지:** "이미지를 언제 저장할지 결정하는 것이, 이미지를 저장할지 말지 결정하는 것보다 더 중요했다."

**왜 이 글이 강력한가:** 이진적 결정("저장한다/안 한다")이 아니라 비용 발생 시점을 설계 대상으로 본 시각을 보여줌. "기능을 빼는 결정"에서 한 단계 더 나아가 "언제 비용을 발생시킬 것인가"를 판단한 사례 — 시니어/리더십 시그널.

**도입부 훅:**
> 처음 설계는 단순했다. "밈을 뽑으면 이미지가 만들어진다. 그러면 그걸 저장해야지." Cloudflare R2에 S3 호환 SDK로 업로드하는 코드까지 다 짰다. 그리고 다 지웠다. 그렇다고 R2를 완전히 버린 건 아니었다.

**섹션 구조:**
1. **초기 설계** — 합성 이미지 → R2 업로드 → DB에 URL 기록 (TASK-260429-19)
2. **무엇이 거슬렸나** — 고아 파일(DB 저장 실패 시 R2만 남음), 보상 트랜잭션 필요, R2 권한·CORS 관리
3. **다시 본 요구사항** — "사용자는 결과 카드를 본다. 저장된 카드를 다시 본다. 다운로드한다."
4. **본질** — 사용자에게 필요한 건 "이미지 파일"이 아니라 "재현 가능한 카드". **재료(이미지 URL + 말풍선 위치 + 문구)** 만 JSONB로 저장하면 된다.
5. **새 설계** — `user_memes.composition` JSONB 한 컬럼이 모든 것을 담는다
6. **트레이드오프**
   - ✅ 고아 파일 없음, 백업 단순, 뽑기 비용 0
   - ⚠️ 다운로드는 클라이언트 렌더링(`html2canvas`) — 폰트/CSS 한계
   - ✅ OG 이미지(링크 미리보기)는 **공유 클릭 시점에만** R2 Lazy 업로드로 해결 (`docs/og-image-plan.md`)
7. **OG 이미지는 어떻게 풀었나 — Lazy 업로드 전략**
   - 뽑기할 때마다 R2에 올리지 않는다. 공유하기를 누른 사람만, 그 시점에 최초 1회만 업로드
   - R2 경로 분리: 소스 이미지 `meme-images/` vs OG 전용 `og/{memeId}.png`
   - 비용이 실제 공유 의사가 있는 사람에게만 발생 → 비용-가치 비율 최적
   - 이 설계가 "모든 결과를 R2에 저장"을 철회한 결정과 충돌하지 않는 이유

**비주얼 컴포넌트 추천:**
- Before/After 2열 비교 — 좌: 뽑기마다 R2 업로드 흐름 / 우: JSONB 저장 + Lazy OG 업로드 흐름
- 코드 블록 — `composition` JSONB 예시 (imageUrl, subjectPosition, phraseText 5줄)
- 통계 카드 — 제거한 코드 라인 수 (R2 업로드 dead code 399줄 제거 PR #100)
- 흐름 박스 — "공유하기 클릭 → og_image_url 있으면 바로 공유 / 없으면 캡처 → R2 업로드 → 저장 → 공유" 3단계

**lesson-box:**
> 처음 설계는 "필요할지 모른다"는 가정 위에 쌓이기 쉽다. "지금 필요한가"를 묻고, 아니라면 git이 기억하게 둔다. 그리고 정말 필요해졌을 때는, 처음부터 전부 저장할 필요 없이 — 비용이 발생하는 시점을 늦추면 된다.

**다음 글 연결:** "저장은 단순해졌지만, 조회 빈도가 늘자 캐시가 필요해졌다 → post10"

### 📄 post6 — "OAuth2 state가 사라진다 — STATELESS의 함정"

**카테고리:** 피카밈 개발기 · 이슈 #4
**한 줄 메시지:** "무상태 서버에 상태가 필요한 흐름(OAuth2)이 들어오면, 그 상태를 어디에 둘지부터 정해야 한다."

**왜 이 글이 강력한가:** post4와 짝꿍 (둘 다 보안/세션 영역). OAuth2 내부 흐름을 이해하고 있다는 시그널.

**섹션 구조:**
1. **현상** — `[authorization_request_not_found]` 에러
2. **OAuth2 state란?** — CSRF 방지 토큰, 카카오/구글로 보낸 후 콜백에서 검증해야 함
3. **Spring 기본 동작** — state를 HTTP 세션에 저장 → 콜백에서 꺼냄
4. **충돌** — JWT 기반 서비스에서 `SessionCreationPolicy.STATELESS`로 두면 세션이 없음 → state 저장 불가
5. **잘못된 복구** — `IF_REQUIRED`로 풀어주면 JSESSIONID가 생김 → JWT 삭제해도 세션으로 재인증됨 (post4와 연결)
6. **해결** — `CookieOAuth2AuthorizationRequestRepository` (state를 짧은 TTL 쿠키에 직렬화)
7. **숨은 함정** — `authorizationEndpoint`만 설정하면 리다이렉트 필터에만 적용됨 → `OAuth2LoginAuthenticationFilter`도 `ObjectPostProcessor`로 직접 wiring 필요

**비주얼 컴포넌트 추천:**
- 시퀀스 다이어그램 (간단) — 프론트 → 백엔드 → 카카오 → 콜백 4단계 + state 흐름
- 코드 블록 — Spring Security 설정 핵심 부분
- 흐름 박스 — 잘못된 흐름 vs 올바른 흐름 2단

**lesson-box:**
> 라이브러리의 "기본 동작"은 당신 서비스의 "기본 가정"과 항상 일치하지 않는다. 한 번 깊이 들어가 본 흐름이, 다음 비슷한 문제의 시간을 절약한다.

**한 줄 메시지:** "다음 프로젝트에서 절대 반복하지 않을 5가지."

**왜 이 글이 강력한가:** 회고는 "성장 곡선"을 보여주는 가장 직접적 증거. 면접관이 가장 빠르게 읽고 가장 강하게 기억하는 글.

**섹션 구조:**

2. **무엇을 다시 안 할 것인가**

   - ② "필요할지 모르는" 코드는 안 쓴다 (R2 dead code 399줄 삭제)

   - ⑤ AI에게 코드를 시키기 전에, AI에게 "규칙"을 먼저 시킨다 (AIRULES.md)
3. **AI 협업의 솔직한 회고**
   - 잘한 것: 반복 작업 가속, 보일러플레이트, 마이그레이션 작성
   - 못한 것: 문맥 망각, 안전한 변경 vs 과감한 변경 판단, 도메인 규칙 무시
   - 결론: AI는 코드를 빠르게 짜지만, "맞는 코드"를 짜게 만드는 건 결국 사람
4. **다음 프로젝트의 화두** — 1개의 명확한 가설, 1주일 안 배포 가능한 MVP, 처음부터 i18n 고려

**비주얼 컴포넌트 추천:**
- 통계 카드 (3-4개) — 숫자로 보여주기
- 타임라인 — 1개월 주요 마일스톤 (Phase 1 종료, v2 재설계, 배포, 미션 도입, i18n)
- 정리 박스 — "다시 안 할 5가지" 리스트
- highlight-box — 마지막 한 줄

**lesson-box (최종):**
> 기술은 진보의 수단이지 증명의 수단이 아니다. 누구를 위해, 왜, 지금 만드는가 — 그게 모든 결정의 기준이었다.

## 4. 나머지 6편 간단 골격 (메모 수준)

### post7 — Rate Limiting 전략 (⭐⭐)
- 훅: "Cloudflare가 막아주는데 왜 Redis까지 써서 Rate Limit을 만들었나"
- 핵심: 대량 DDoS vs 저속 DDoS (내부 비용 폭탄)
- 엔드포인트별 위험도: compose(CPU) > OAuth(세션) > GET
- 토큰 버킷 알고리즘, fail-closed 정책
- `RATE_LIMIT_USE_FORWARDED_HEADERS` — IP 식별의 함정 (Cloudflare 우회)

### post8 — 미션 시스템 접점 버그 (⭐)
- 훅: "미션 시스템을 만들었는데, 깨진 건 미션이 아니었다"
- 핵심: 비로그인 가드 누락, 잔액 0 체크 누락, `chargeIfNeeded` 이후 캡처 버그
- 메시지: "새 기능은 기존 시스템과의 접점에서 터진다"

### post9 — i18n 백엔드 vs 클라이언트 (⭐⭐)
- 훅: "한국어 전용이었던 서비스에 영어를 더하는 결정은, 코드보다 먼저 책임 분리부터다"
- 핵심: Spring MessageSource vs error.code 패턴
- 밈 문구 다국어: language 컬럼 vs JSONB vs 별도 테이블
- 참조: `docs/i18n-fullstack-plan.md` 그대로 활용 가능

### post10 — @Cacheable의 숨은 함정 (⭐)
- 훅: "어노테이션 한 줄로 Redis가 붙는 건 마법이 아니라, 누군가 만든 추상화다"
- AOP 프록시, self-invocation 함정, 제네릭 타입 직렬화 (`activateDefaultTyping`)
- TTL은 짧게, invalidate 로직은 안 만든다 — 트레이드오프

### post11 — Cloudflare Polish (⭐)
- 훅: "코드 한 줄 안 쓰고 이미지 용량을 절반으로 줄였다"
- Polish (Lossy), Edge TTL, R2 도메인 단일화 (`pub-*.r2.dev → img.pick-a-me.me`)
- 운영의 가치: "코드 vs 설정" 균형 감각

### post3.5 또는 다른 위치 — 폰트 랜덤화 (선택, ⭐)
- 가장 최근 작업 (TASK)이므로 신선도 있음
- "Pretendard는 너무 깔끔했다 — 밈에는 폰트도 랜덤이 필요했다"
- seed 기반 결정론적 랜덤, 언어별 풀 분기, html2canvas와 폰트 로딩 동기화
- 짧은 글 (5분), 디자인적 사고를 보여주는 의외의 어필 포인트

## 5. 작성 팁 (포트폴리오 효율 극대화)

### 5-1. 첫 3문장 룰
독자(특히 채용 담당자)는 첫 3문장에서 읽을지 말지 결정한다. 모든 글의 첫 3문장은:
1. **구체적 사건/숫자**로 시작 ("로그아웃 버튼을 누르면 토스트가 뜬다. 새로고침하면 다시 로그인 상태다.")
2. 추상적 단어 금지 ("이번에는 인증 시스템에 대해 알아보겠습니다" ❌)
3. 1인칭 + 능동태 ("나는 ~을 했다")

### 5-2. 코드 블록 분량
- 한 글에 코드 블록 3개 이내
- 한 블록은 15줄 이내 (스크롤하게 만들지 마라)
- "전체 구현"이 아니라 "결정의 증거"만 노출

### 5-3. 숫자 강조
포트폴리오 글에선 숫자가 신뢰를 만든다:
- "5차에 걸쳐 수정", "399줄 dead code 삭제", "1주일", "마이그레이션 17개"
- `.stats-grid` 컴포넌트로 시각화

### 5-4. lesson-box는 "추상화"가 아니라 "행동 강령"
- ❌ "보안은 중요하다"
- ✅ "다음 프로젝트에선 인증 흐름을 배포 환경에서 먼저 검증한다"

### 5-5. 외부 참조 (선택)
포트폴리오 리뷰어가 깊이 보고 싶을 때 갈 수 있는 링크:
- GitHub 저장소, 특정 PR (예: PR #100 — dead code 삭제)
- 관련 docs (예: `docs/known-issues.md` BUG-07 섹션)
- 단, 본문에 직접 박지 말고 글 말미에 `.references` 박스로
