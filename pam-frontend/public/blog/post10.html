어노테이션 1줄이 하는 일

피카밈의 뽑기 흐름에서 가장 빈번하게 조회되는 데이터는 "최근 태그 매칭된 밈 목록"이다. 뽑기를 할 때마다 DB에서 선택 기준 후보를 조회하는 쿼리가 발생한다. 캐싱 대상으로 적합했다.

// JpaUserMemeRepositoryAdapter.kt @Cacheable("recent-matched-memes") override fun findRecentTagMatched(limit: Int): List<UserMeme> = jpaRepository.findRecentTagMatched(limit) .map { it.toDomain() }

겉에서 보면 1줄이다. 하지만 이 줄이 작동하기까지 배경이 생각보다 많다.

AOP 프록시 계층

Spring의 @Cacheable은 AOP(Aspect-Oriented Programming) 방식으로 구현된다. 빈 등록 시 Spring이 원본 클래스를 감싸는 프록시 객체를 대신 주입한다. 메서드 호출이 들어오면 프록시가 먼저 가로채서 캐시를 확인하고, 히트이면 실제 메서드를 호출하지 않고 캐시 값을 반환한다.

1
호출자 (MemeComposeService)
의존성 주입받은 빈이 실제로는 프록시임을 모른다
↓ 메서드 호출
2
CGLIB 프록시
캐시 키 생성 → Redis 조회 → 히트이면 3번 스킵, 미스이면 3번 실행 후 결과를 Redis에 저장
↓ 캐시 미스 시에만
3
JpaUserMemeRepositoryAdapter
실제 메서드 실행 → DB 쿼리 → List<UserMeme> 반환

Spring이 Bean으로 등록할 때 원본 클래스 대신 CGLIB이 생성한 서브클래스를 주입한다. 외부에서 보면 평범한 빈처럼 보이지만, 실제로는 프록시다.

self-invocation 함정

프록시 구조에서 생기는 함정이 하나 있다. 같은 클래스 내부에서 @Cacheable이 붙은 메서드를 호출하면 캐시가 작동하지 않는다.

// 이런 코드는 캐시가 작동하지 않는다 class JpaUserMemeRepositoryAdapter : UserMemeRepository { @Cacheable("recent-matched-memes") override fun findRecentTagMatched(limit: Int): List<UserMeme> = ... fun someOtherMethod() { // this.findRecentTagMatched()는 프록시를 거치지 않는다 // — 같은 객체 내부 직접 호출이므로 AOP 인터셉터가 없다 val memes = findRecentTagMatched(10) // 캐시 미작동 } }

프록시는 외부에서 들어오는 호출만 인터셉트한다. 같은 객체에서 this.메서드()로 호출하면 프록시를 건너뛰고 실제 메서드가 바로 실행된다. 캐시가 붙어 있는 것처럼 보이지만 항상 DB 쿼리가 발생한다.

피카밈에서는 findRecentTagMatched를 항상 외부 서비스(MemeComposeService)가 호출하므로 self-invocation 문제가 없다. 하지만 인프라 레이어 내부에서 같은 클래스의 캐시 메서드를 호출하는 구조를 만들었다면 조용히 실패했을 것이다.

제네릭 타입 직렬화 이슈

Redis에 List<UserMeme>을 저장하려면 직렬화와 역직렬화 과정에서 제네릭 타입 정보가 보존되어야 한다. 기본 Jackson 설정만으로는 역직렬화 시 UserMeme의 타입 정보가 소실되어 LinkedHashMap으로 역직렬화된다.

이 문제를 해결한 것이 activateDefaultTyping이다.

// RedissonConfig.kt — cacheManager 설정 val objectMapper = ObjectMapper() .registerModule(kotlinModule()) .registerModule(JavaTimeModule()) .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS) .activateDefaultTyping( BasicPolymorphicTypeValidator.builder() .allowIfBaseType(Any::class.java) .build(), ObjectMapper.DefaultTyping.NON_FINAL ) // → 직렬화 시 타입 정보를 JSON에 포함: ["com.pickameme.domain.meme.UserMeme", {...}] // → 역직렬화 시 타입 복원 가능

activateDefaultTyping은 JSON에 타입 정보를 함께 기록한다. ["com.pickameme.domain.meme.UserMeme", {…}] 형태로 저장된다. 역직렬화할 때 이 정보를 읽어 정확한 타입으로 복원한다. 보안 측면에서는 allowIfBaseType(Any::class.java)로 허용 타입 범위를 제한했다.

캐시 키에 언어를 포함해야 하는 이유

post9에서 다룬 i18n 작업에서 findRecentTagMatched에 language 파라미터를 추가하기로 했다. 이때 캐시 키 설계에 함정이 있다.

파라미터를 추가하면 Spring은 기본적으로 모든 파라미터를 캐시 키에 포함한다. findRecentTagMatched(limit=10, language="ko")와 findRecentTagMatched(limit=10, language="en")는 다른 키를 갖는다. 이건 원하는 동작이다.

문제는 언어 파라미터를 추가하지 않고 별도 로직으로 처리하거나, @Cacheable(key = "#limit")처럼 키에서 언어를 명시적으로 제외했을 때다. 한국어 요청이 캐시한 List<UserMeme>에 영어 문구가 섞인 결과를 영어 요청이 받아갈 수 있다.

캐시 키는 "같은 입력이면 같은 출력"이라는 계약이다. 출력에 영향을 미치는 모든 인자가 키에 포함되어야 한다. 언어가 출력을 바꾼다면, 언어는 키에 들어가야 한다.

TTL로 invalidation을 회피하다

캐시 전략에서 가장 어려운 문제 중 하나는 캐시 무효화(invalidation)다. 피카밈에서는 이를 TTL로 회피했다.

RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofMinutes(10)) — 모든 캐시의 기본 TTL이 10분이다. 데이터가 변경되면 10분 이내에 자연스럽게 만료된다. @CacheEvict를 써서 저장 시점에 캐시를 명시적으로 삭제할 수도 있지만, 그 경우 삭제 로직과 저장 로직이 결합된다.

뽑기 결과 목록에서 10분의 지연은 허용 가능한 수준이다. "최근 태그 매칭된 밈"이 10분 전 데이터를 보여줘도 서비스 품질에 영향이 없다. 허용 가능한 지연이 있다면 TTL이 invalidation 로직보다 간단하고 안전하다.

이 경험에서 배운 것

어노테이션 1줄은 코드가 적다는 것이지, 동작이 단순하다는 것이 아니다. AOP 프록시, 타입 직렬화, 캐시 키 설계, TTL 정책 — 1줄 뒤에 이것들이 있다.

캐시를 쓸 때 가장 먼저 물어야 할 것은 "무엇이 이 메서드의 출력을 결정하는가"다. 그 모든 요인이 캐시 키에 들어가야 한다. 요인이 빠지면 다른 입력이 같은 캐시를 공유하게 되고, 그건 조용한 버그다.
