하트가 두 종류인 이유

처음 설계할 때는 하트를 하나로 통일하려 했다. 하트는 하트 아닌가. 근데 설계를 이어가다 보니까 두 종류의 성격이 너무 달랐다. 충전 방식도 다르고, 중요도도 달랐다. 같은 저장소에 넣으면 결국 어느 쪽에도 최적화가 안 된다.

BASIC 하트 — Lazy Charging

BASIC 하트는 빠르게 쓰고 빠르게 차오르는 게 목적이다. 5분마다 1개, 최대 5개. 모바일 게임의 스태미너 시스템과 같은 구조다.

Redis를 SSOT로 쓴 이유는 실시간성 때문이다. 사용자가 "지금 하트 몇 개야?"를 자주 확인한다. DB에 넣으면 읽기 속도가 문제가 되고, 충전 체크 로직을 매번 돌리기엔 부담스럽다.

대신 충전 방식은 Lazy Charging을 쓴다. 5분마다 배치 잡을 돌리는 게 아니라, 조회 시점에 "마지막 충전 이후 얼마나 지났는지"를 계산해서 그 자리에서 채워준다. 배치 없이 서버 자원을 아끼는 방법이다.

SPECIAL 하트 — 정합성이 우선

SPECIAL 하트는 희소성이 핵심이다. 로그인 첫날 지급, 특정 밈을 N회 공유했을 때, 이벤트 달성 시 — 조건에서 생긴다. 자주 충전되지 않는 만큼 한 개 한 개가 의미 있어야 한다.

JPA/DB를 SSOT로 쓴 이유는 정합성 때문이다. SPECIAL 하트는 지급 내역이 정확히 기록돼야 한다. 나중에 "왜 이 사용자한테 하트가 지급됐는지" 추적할 수 있어야 하고, 중복 지급이 절대 없어야 한다. Redis는 이런 영속성 보장에 적합하지 않다.

같은 재화라도 성격이 다르면 저장소가 달라야 한다. 빠른 것과 정확한 것은 같은 곳에 최적화할 수 없다.

Race Condition

하트 소모 로직을 처음 짤 때는 단순했다. "현재 하트 수 읽기 → 1 빼기 → 저장." 근데 여기에 구멍이 있었다.

사용자가 뽑기 버튼을 빠르게 두 번 연속으로 누르면 어떻게 될까. 두 요청이 동시에 들어오면, 둘 다 Redis에서 "현재 하트 3개"를 읽을 수 있다. 둘 다 3에서 1을 빼서 2로 저장하면 — 하트를 2개 썼는데 1개만 빠진다.

1
요청 A, B 동시 도착 → 둘 다 Redis에서 하트 잔량 읽음 (3개)
2
A가 3 − 1 = 2 저장. B도 3 − 1 = 2 저장
3
결과: 하트 2개 사용 → 잔량 2개 (실제론 1개여야 함)

테스트 환경에서는 잘 안 잡힌다. 혼자 조용히 쓰면 동시 요청이 없다. 실제 사용자가 몰리거나, 네트워크가 늦어서 요청이 겹칠 때 터진다. Pet-Pass에서 이런 종류의 버그를 뒤늦게 발견한 적이 있었기 때문에, 피카밈에서는 처음부터 설계에 포함시켰다.

분산 락으로 막는다

해결책은 Redisson 분산 락이다. 하트 소모/충전 로직에 진입하기 전에 Redis에서 락을 획득하고, 작업이 끝나면 락을 해제한다. 락을 못 얻으면 짧게 대기하다가 재시도한다.

1
요청 A 도착 → heart:lock:{userId} 락 획득
2
요청 B 도착 → 락 획득 실패 → 대기
3
A가 하트 3 → 2로 저장, 락 해제
4
B가 락 획득 → 하트 2 → 1로 저장, 락 해제

락 범위는 사용자 단위다. A의 락이 B의 요청을 막으면 안 된다. 키를 heart:lock:{userId}로 잡아서 사용자별로 독립적으로 락이 걸린다. 이렇게 하면 서로 다른 사용자의 요청은 아무 영향 없이 병렬로 처리된다.

비로그인 하트 — 서버가 없다

비로그인 사용자도 밈을 뽑을 수 있다. 근데 비로그인인데 하트를 서버에서 관리하면 문제가 생긴다. 계정도 없는 사람의 하트를 Redis에 저장하면 무한정 쌓이고, 만료 기준도 모호해진다.

그래서 비로그인 하트는 localStorage SSOT로 처리한다. 하트 잔량, 마지막 충전 시각 — 전부 브라우저에 저장한다. 서버 API 호출이 없다. useGuestHeart 훅이 Lazy Charging 계산을 직접 한다.

단점은 있다. 탭을 닫으면 밈 히스토리가 사라지고, 다른 기기에서 이어서 쓸 수 없다. 그 불편함이 자연스럽게 "로그인하면 저장돼요"로 연결된다. 불편함 자체가 UX 설계의 일부였다.

이 경험에서 배운 것

같은 개념(하트)이라도 성격이 다르면 저장소를 분리하는 게 맞다. 두 요구사항이 충돌하면 하나를 희생시키거나, 아니면 처음부터 분리해야 한다.

동시성 문제는 트래픽이 작을 때는 보이지 않는다. 설계 단계에서 "이 로직이 동시에 두 번 호출되면 어떻게 되는가"를 물어보는 습관이 필요하다. 분산 락은 무거운 도구지만, 필요한 곳에는 처음부터 쓰는 게 낫다.
