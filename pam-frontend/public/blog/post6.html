사건의 발단

카카오, 구글 소셜 로그인을 구현했다. 로컬 환경에서 양쪽 다 잘 됐다. 배포 후 며칠간은 문제없었다. 그러다 갑자기 로그인 버튼을 눌렀을 때 카카오 인증 화면까지 넘어갔다가 돌아오면 에러 페이지로 떨어졌다.

Spring Security 로그에 찍힌 메시지는 딱 한 줄이었다.

[authorization_request_not_found]

요청이 발견되지 않았다는 게 무슨 뜻인가. 로그인 버튼을 분명히 눌렀는데, 요청이 없다고 한다.

OAuth2 state란

OAuth2 인가 코드 흐름에는 state라는 파라미터가 있다. 짧은 랜덤 문자열이다. CSRF 공격을 막기 위한 장치다.

핵심은 두 번째 행이다. 백엔드가 state를 생성한 뒤 어딘가에 저장해둬야 한다. 카카오에서 콜백이 돌아왔을 때 그걸 꺼내서 비교해야 하니까. 그 "어딘가"가 문제였다.

Spring의 기본 동작

Spring Security의 기본 구현인 HttpSessionOAuth2AuthorizationRequestRepository는 이름 그대로 state를 HTTP 세션에 저장한다. 로그인 요청 시 세션에 넣고, 콜백에서 세션에서 꺼낸다.

세션 기반 앱에서는 자연스러운 선택이다. 그런데 피카밈은 세션을 쓰지 않는다.

STATELESS와의 충돌

피카밈은 JWT HttpOnly 쿠키로 인증한다. 서버 사이드 세션이 없다. SecurityConfig에 명시적으로 선언되어 있다.

// 세션을 완전히 끄는 선언 http.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) }

이 한 줄이 문제의 근원이었다. STATELESS 정책 하에서 Spring Security는 세션을 생성하지 않는다. state를 저장할 세션이 없으니, 콜백에서 꺼낼 state도 없다. [authorization_request_not_found]는 이 상황을 그대로 표현한 것이다.

OAuth2는 인가 요청과 콜백 사이에 상태(state)를 보존해야 하는 흐름이다. 무상태 서버에 상태가 필요한 흐름이 들어오면, 그 상태를 어디에 둘지부터 정해야 한다.

잘못된 복구 — IF_REQUIRED

1차 시도 · 실패

가장 빠른 해결책처럼 보인 것은 세션 정책을 IF_REQUIRED로 완화하는 것이었다. OAuth2 흐름에서만 세션을 허용하자는 의도였다. state 저장 에러는 사라졌다. 로그인이 됐다.

그런데 이 수정에는 대가가 있었다. IF_REQUIRED는 Spring이 필요하다고 판단할 때마다 세션을 만든다. OAuth2 핸드셰이크 과정에서 JSESSIONID 쿠키가 생겼다. 그리고 이 세션은 JWT가 만료되거나 삭제되어도 살아남아 사용자를 계속 인증 상태로 유지시켰다.

post4에서 로그아웃이 5번 깨진 원인 중 마지막 하나가 바로 이것이었다. JWT를 지워도 JSESSIONID가 남아서 백엔드가 세션으로 사용자를 재인증했다. 잘못된 복구가 다른 버그의 원인이 되어 있었다.

해결 — 쿠키가 세션을 대신한다

해결 · CookieOAuth2AuthorizationRequestRepository

세션 대신 단기 HttpOnly 쿠키에 state를 직렬화해서 저장한다. 세션을 생성하지 않으면서도 요청-콜백 사이에 state를 전달할 수 있다.

CookieOAuth2AuthorizationRequestRepository를 직접 구현했다. 동작은 단순하다. 로그인 요청 시 OAuth2AuthorizationRequest 객체를 Java 직렬화 + Base64로 인코딩해서 oauth2_auth_request 쿠키에 담는다. TTL은 180초 — OAuth2 흐름이 3분을 넘기는 일은 없다. 콜백에서 쿠키를 읽어 역직렬화하고, 검증 후 즉시 쿠키를 지운다.

// CookieOAuth2AuthorizationRequestRepository — 핵심 저장 로직 override fun saveAuthorizationRequest( authorizationRequest: OAuth2AuthorizationRequest?, request: HttpServletRequest, response: HttpServletResponse ) { val cookie = ResponseCookie.from("oauth2_auth_request", serialize(authorizationRequest)) .httpOnly(true) .secure(true) .sameSite("Lax") .maxAge(180) // 3분 TTL — 흐름 완료 후 자동 소멸 .build() response.addHeader("Set-Cookie", cookie.toString()) }

쿠키가 세션의 역할을 대신하지만 서버 사이드 상태는 없다. 완전한 STATELESS를 유지하면서 OAuth2 흐름이 요구하는 임시 상태를 브라우저 측에서 관리하는 방식이다.

숨은 함정 — 절반만 연결된 설정

CookieOAuth2AuthorizationRequestRepository를 만들고 SecurityConfig에 연결했다. 그런데 여전히 간헐적으로 [authorization_request_not_found]가 터졌다.

OAuth2 로그인 흐름에는 두 개의 필터가 관여한다. 로그인 요청을 처리해서 카카오/구글로 리다이렉트하는 OAuth2AuthorizationRequestRedirectFilter, 그리고 콜백을 받아서 토큰을 교환하는 OAuth2LoginAuthenticationFilter다.

authorizationEndpoint에만 저장소를 설정하면 리다이렉트 필터에는 쿠키 저장소가 연결되지만, OAuth2LoginAuthenticationFilter는 여전히 기본 세션 저장소를 바라본다. state를 쿠키에 저장했는데 콜백에서는 세션에서 꺼내려 하니 당연히 찾지 못한다.

// SecurityConfig — 두 필터 모두에 쿠키 저장소를 연결해야 한다 .oauth2Login { oauth2 -> // ① 리다이렉트 필터에 연결 oauth2.authorizationEndpoint { it.authorizationRequestRepository(cookieAuthorizationRequestRepository) } // ② 콜백 필터에도 직접 주입 — 이걸 빠뜨리면 절반만 연결된다 .withObjectPostProcessor( object : ObjectPostProcessor<OAuth2LoginAuthenticationFilter> { override fun <O : OAuth2LoginAuthenticationFilter> postProcess(filter: O): O { filter.setAuthorizationRequestRepository(cookieAuthorizationRequestRepository) return filter } } ) }

ObjectPostProcessor로 OAuth2LoginAuthenticationFilter가 생성된 직후에 저장소를 교체 주입했다. 이 한 줄이 추가되고 나서야 에러가 완전히 사라졌다.

이 경험에서 배운 것

라이브러리의 "기본 동작"은 당신 서비스의 "기본 가정"과 항상 일치하지 않는다. Spring Security의 OAuth2 구현은 세션 기반 앱을 가정한다. JWT + STATELESS 서비스에서 그대로 쓰면 충돌한다.

그리고 설정이 "연결된 것처럼 보이는 것"과 "실제로 연결된 것" 사이에는 차이가 있다. OAuth2 흐름에 필터가 두 개라는 사실을 알기 전까지는 왜 간헐적으로 터지는지 이해할 수 없었다. 프레임워크 코드를 한 번 직접 따라가 본 시간이 두 번째 이후의 같은 종류의 문제를 빠르게 해결하게 해줬다.
