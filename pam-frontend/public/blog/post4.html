로그아웃이 안 풀렸습니다

로그아웃 버튼을 누르면 인앱 토스트가 떴습니다. "로그아웃 되었습니다."
안심하고 화면을 새로고침했거든요. 그런데 제 프로필과 하트 수치가 로그인된 상태 그대로 다시 살아 있더라고요. 1시간 안에 끝날 줄 알았던 이 사소한 기능을, 결국 장장 5차례에 걸쳐 디버깅하고 나서야 겨우 잡았습니다.

보안 기능은 정상 동작할 때보다 비정상 상황에서 그 실체가 드러나더라고요. 쿠키와 세션과 토큰은 단순히 넣고 빼는 변수가 아니라 브라우저가 저마다 다르게 해석하는 "정책으로 격리된 자원"이었거든요.

피카밈의 기본 인증 아키텍처는 이렇습니다. 카카오나 구글 소셜 로그인이 성공하면 백엔드가 JWT를 생성해 HttpOnly; Secure; SameSite=Lax 쿠키(`pam_token`)로 클라이언트에 심습니다. 브라우저는 다음 API 호출부터 이 쿠키를 자동으로 실어 보내고요. 그렇다면 로그아웃은 단순히 해당 쿠키를 만료(Max-Age=0)시켜 브라우저에서 지워주면 끝나는 문제였습니다. 적어도 이론상으로는 그랬거든요.

1차 — React Query 캐시를 의심하다

1차 시도 · 실패

로그아웃 버튼을 눌렀는데도 제 프로필이 살아 있길래, 처음엔 "React Query의 인메모리 캐시가 stale 상태로 갱신되지 않고 화면에 남아있는 거구나" 싶었거든요.

곧바로 로그아웃 핸들러에 queryClient.clear()를 추가했습니다. 확실히 화면상의 데이터는 그 순간 즉시 사라지더라고요. 그런데 새로고침을 누르자마자 다시 로그인 정보가 되살아났습니다. 캐시가 문제가 아니었거든요. 새로고침 시 백엔드로 보내는 `/api/auth/me` 요청에 여전히 유효한 JWT 쿠키가 실려 날아가고 있었습니다. 브라우저 저장소 수준에서 쿠키가 아예 삭제되지 않은 거였어요.

2차 — 크로스 오리진 fetch의 장벽

2차 시도 · 실패

크롬 개발자 도구의 Network 탭을 열어 로그아웃 API 응답 헤더를 추적했습니다. 백엔드는 분명하게 Set-Cookie: pam_token=; Max-Age=0; Path=/ 헤더를 내려보내고 있었거든요. "그런데 왜 브라우저는 쿠키를 만료시키지 않고 버젓이 쥐고 있는 걸까?" 하는 생각이 들었습니다.

원인은 브라우저의 **크로스 오리진 요청에 대한 쿠키 적용 차단 정책**이었습니다. 피카밈 프론트엔드는 pick-a-me.me에, 백엔드 API는 api.pick-a-me.me에 배포되어 있거든요. JS 코드의 비동기 fetch() 호출은 크로스 오리진 XHR 요청에 해당하니까, 브라우저는 보안상의 이유로 응답 헤더의 Set-Cookie 설정을 가차 없이 무시해 버립니다.

물론 credentials: 'include' 옵션을 fetch에 주고 CORS 설정을 허용해주면 해결되는 것처럼 보이긴 했습니다. 그렇지만 좀 더 확실하고 과하지 않은 해결책을 택했어요. 비동기 백그라운드 fetch를 버리고, 로그아웃 버튼을 눌렀을 때 브라우저의 최상단 네비게이션 자체를 백엔드 오리진으로 직접 이동시키는 **탑레벨 GET 네비게이션** 방식을 쓴 거죠.

// [프론트엔드] fetch를 걷어내고 브라우저 네비게이션으로 강제 전환 const handleLogout = () => { // 비동기 fetch 대신 백엔드 오리진으로 직접 페이지 이동 window.location.href = `${API_BASE}/api/auth/logout`; };

이제 브라우저가 직접 페이지를 이동하니까 크로스 오리진 제약 없이 백엔드가 보내는 쿠키 만료 헤더가 깔끔하게 먹히기 시작했습니다. 로컬 환경에서의 검증은 보기 좋게 성공했고요. 그런데 안심하고 운영 서버에 배포한 순간, 버그가 다시 부활하더라고요.

3차 — 쿠키 domain 불일치의 늪

3차 시도 · 실패

분명 로컬에선 삭제되던 쿠키가 운영 배포 서버에서는 새로고침을 하면 계속 부활했거든요. 원인을 밝히려고 브라우저 Application 탭의 Cookie 저장소를 뒤져보다가 의외의 사실을 발견했습니다.

브라우저 저장소 안에 이름은 같은데 **domain 속성이 완전히 다른 두 개의 `pam_token` 쿠키**가 나란히 공존하고 있더라고요. 하나는 배포 전환 과정에서 쿠키 도메인을 지정하기 전에 생성된 `pam_token (domain 없음)`, 다른 하나는 도메인이 명시된 `pam_token (domain=.pick-a-me.me)`였습니다.
브라우저는 이름이 같더라도 도메인 속성이 다르면 완전히 별개의 쿠키로 취급하거든요. 백엔드가 `domain=.pick-a-me.me`를 붙여 만료 헤더를 보냈으니까, 배포 전 구형 쿠키는 삭제되지 않고 좀비처럼 살아남아 인증을 계속 유효하게 만들고 있었던 거죠.

이걸 해결하려고 백엔드 로그아웃 핸들러에서 **도메인이 설정된 버전과 설정되지 않은 버전, 두 가지 만료 쿠키를 동시에 응답 헤더에 실어보내는 다중 만료 전략**을 썼습니다.

// [백엔드 AuthController.kt] 두 속성의 쿠키를 동시 삭제 요청 val cookieDomain = ".pick-a-me.me" // 1. domain이 명시되지 않은 구버전 쿠키 만료 response.addHeader("Set-Cookie", "pam_token=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax") // 2. domain이 명시된 신버전 쿠키 만료 response.addHeader("Set-Cookie", "pam_token=; Domain=$cookieDomain; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax")

도메인 불일치로 생긴 좀비 쿠키가 완전히 사라졌습니다. 드디어 끝난 줄 알았는데, 사파리와 일부 크롬 사용자에게서 여전히 새로고침 시 로그인 상태가 풀리지 않는다는 제보가 잇따르더라고요.

4차 — Host-Only 쿠키의 주권과 리다이렉트 릴레이

4차 시도 · 실패

이유는 브라우저 쿠키 보안 정책의 핵심인 **Host-Only 쿠키의 강력한 격리 제약** 때문이었거든요.

백엔드 API 서버(`api.pick-a-me.me`)가 발급한 host-only 쿠키는, 아무리 parent domain인 `.pick-a-me.me`가 만료를 외쳐도 **오직 발급 호스트인 `api.pick-a-me.me` 본인만이 만료시킬 수 있는 절대 주권**을 가지더라고요.
브라우저가 API 통신을 할 때 살아 있는 `api.pick-a-me.me` host-only 쿠키를 함께 전송하니까, 프론트에서 아무리 지우려 애써도 백엔드 필터가 잔존 쿠키를 읽고 로그인을 복원해 버렸거든요.

결국 프론트엔드와 백엔드가 서로 상대방의 host-only 영역을 침범해 삭제할 수 없으니, **두 오리진을 브라우저가 순차적으로 릴레이 방문해서 각자의 쿠키를 본인 주권 아래 소멸시키는 쿠키 서킷(Circuit)**을 설계할 수밖에 없었습니다.

🔄 양방향 쿠키 소멸 리다이렉트 서킷

1
유저가 프론트엔드 로그아웃 리다이렉터(pick-a-me.me/api/auth-logout) 진입 ➔ 프론트 Host-Only 및 Parent-Domain 쿠키 만료
↓ 307 Redirect
2
백엔드 로그아웃 엔드포인트(api.pick-a-me.me/api/auth/logout)로 자동 점프 ➔ 백엔드 Host-Only 및 Configured-Domain 쿠키 만료
↓ 302 Redirect
3
프론트엔드 홈(pick-a-me.me/)으로 최종 도달 ➔ 모든 영역의 쿠키가 100% 영구 전멸

양 도메인의 주권 아래 호스트 쿠키를 각각 지우고 복귀하는 이 릴레이 서킷 설계로, 드디어 모든 브라우저에서 쿠키가 깨끗하게 비워졌습니다. 그런데 또다시 로그인 정보가 되살아나는 케이스가 발견되더라고요.

5차 — 잔존하는 JSESSIONID와 Stateless 아키텍처

5차 시도 · 최종 정복 완료

네트워크 트레이스를 해보니 `pam_token`은 단 한 개도 남아 있지 않더라고요. 쿠키가 완벽하게 비워졌는데도 백엔드 `/api/auth/me` API는 여전히 200 OK와 함께 유저 데이터를 반환했습니다. 이 마법 같은 복원의 실마리는 다름 아닌 **세션 쿠키인 `JSESSIONID`**에 있었거든요.

소셜 로그인을 처음 구현할 때 Spring Security OAuth2의 핸드셰이크를 위해 세션 정책을 임시로 SessionCreationPolicy.IF_REQUIRED로 풀어줬던 게 화근이었습니다. OAuth2 과정에서 Spring이 내부적으로 임시 세션을 수립했고, 이 `JSESSIONID` 쿠키가 브라우저에 잔존하면서 `pam_token`이 사라졌는데도 세션 ID를 매개로 백엔드가 사용자를 계속 식별하고 인증 처리해주고 있었던 거죠.

피카밈은 완전한 무상태(Stateless) JWT 기반 서비스여야 하니까, 이 모순을 그냥 둘 수가 없었거든요. OAuth2의 CSRF용 `state` 파라미터 보관을 세션 대신 브라우저의 단기 보안 쿠키로 격리하는 CookieOAuth2AuthorizationRequestRepository를 구현해서 장착했습니다.
그 직후 Spring Security 설정을 엄격한 STATELESS 상태로 되돌렸고요.

// [백엔드 SecurityConfig.kt] 임시 세션 발급을 차단하고 쿠키 저장소 장착 http.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) } http.oauth2Login { it.authorizationEndpoint { auth -> // OAuth2 state 파라미터를 임시 세션이 아닌 보안 쿠키에 저장하도록 연결 auth.authorizationRequestRepository(cookieOAuth2AuthorizationRequestRepository) } }

세션의 흔적을 완전히 지우고 무상태 아키텍처를 온전히 복구하고 나니, 새로고침을 아무리 눌러도 로그인 정보가 부활하는 일은 두 번 다시 없었습니다. 장장 1주일에 걸친 로그아웃의 5중 연쇄 버그가 그제야 잡힌 거죠.

이 험난한 여정에서 남은 것

인증 흐름은 로컬에서 돌아간다고 끝난 게 아니더라고요. 서브도메인이 나뉘는 순간 localhost에서 확인한 동작은 의미가 없어지거든요. 다음 프로젝트에선 쿠키·세션 기능을 처음부터 배포 도메인 기준으로 검증하기로...

Spring Security 설정을 바꿀 때는 그게 다른 필터 체인에 어떤 영향을 주는지부터 봐야겠더라고요. SessionCreationPolicy 하나가 OAuth2 state와 JSESSIONID 양쪽을 동시에 건드렸던 것처럼, 보안 설정은 연쇄 효과가 생각보다 크더라고요.
