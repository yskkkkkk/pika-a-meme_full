현상

로그아웃 버튼을 누르면 토스트가 뜬다. "로그아웃 되었습니다." 새로고침하면 다시 로그인 상태다.

1차에서 멈췄으면 좋았겠지만, 결국 5차까지 갔다. 매번 "이번엔 된 것 같은데?"라고 생각했고, 매번 틀렸다.

보안 기능은 개발 환경에서 고치면 되는 것 같다가도, 배포하면 또 다른 이유로 터진다.

피카밈 인증 구조는 이렇다. 로그인(카카오/구글 OAuth2) 후 백엔드가 JWT를 HttpOnly; SameSite=Lax 쿠키로 발급한다. 이후 API 요청마다 쿠키가 자동으로 붙는다. 로그아웃은 그 쿠키를 삭제하면 된다. 이론상 간단하다.

1차 — React Query 캐시를 의심했다

1차 · 실패

로그아웃 API를 호출하고 나서도 사용자 정보가 남아 있었다. 처음엔 React Query 캐시가 stale 상태로 남아 있어서 그런 거라고 생각했다. queryClient.clear()를 로그아웃 핸들러에 추가했다. 토스트도 정상적으로 뜬다. 새로고침하면 다시 로그인 상태다.

캐시 문제가 아니었다. 새로고침 후에도 로그인 상태가 돌아온다는 건 서버에서 여전히 유효한 JWT를 읽고 있다는 뜻이다. 쿠키가 실제로 지워지지 않았다.

2차 — CORS와 크로스 오리진 쿠키

2차 · 부분 원인 발견

개발자 도구 Network 탭을 보니, 로그아웃 응답에 Set-Cookie: token=; Max-Age=0가 분명히 있었다. 근데 실제로 쿠키가 삭제되지 않았다. 이상했다. 응답은 오는데 왜 적용이 안 되지?

원인은 CORS + credentials 조합에 있었다. fetch로 크로스 오리진 요청을 보낼 때, credentials: 'include'가 없으면 브라우저가 응답의 Set-Cookie를 무시한다. include를 붙이더라도 서버에서 Access-Control-Allow-Credentials: true와 Access-Control-Allow-Origin을 와일드카드가 아닌 명시적 오리진으로 내려줘야 한다.

// 이렇게 하면 Set-Cookie 응답이 있어도 브라우저가 적용하지 않는다 fetch('/api/auth/logout', { method: 'POST' }) // credentials: 'include' 없이는 쿠키가 오가지 않는다 fetch('/api/auth/logout', { method: 'POST', credentials: 'include', })

이걸 고쳤다. 로컬에서 잘 됐다. 배포하면 또 안 됐다.

3차 — 페이지 이동으로 강제 초기화

3차 · 로컬만 됨

router.push('/') 대신 window.location.href = '/'로 바꿔봤다. 소프트 네비게이션 대신 풀 페이지 리로드를 강제하면 React Query 캐시가 초기화되고, 쿠키 상태도 새로 읽힐 거라고 생각했다. 로컬에서는 됐다. 배포에서는 안 됐다.

로컬과 배포의 동작이 다르다는 건 환경이 다르다는 뜻이다. 코드가 아니라 인프라를 봐야 했다.

4차 — domain이 다른 쿠키는 별개다

4차 · 원인 좁혀짐

브라우저의 Application 탭에서 쿠키 목록을 직접 봤다. token이라는 이름의 쿠키가 두 개 있었다. 하나는 domain=localhost, 하나는 domain=pick-a-me.me. 배포하기 전에 로컬에서 로그인했던 쿠키가 남아 있었고, 배포 후 쿠키와 공존하고 있었다. 로그아웃 응답이 배포 쿠키는 지웠지만, 로컬 쿠키는 그대로였다.

로컬 쿠키를 수동으로 지우고 다시 시도했다. 배포 환경에서 새로 로그인해서 로그아웃하면 — 여전히 안 됐다. 로컬 쿠키는 원인이 아니었다. 여전히 뭔가 다른 문제가 있었다.

5차 — host-only 쿠키는 발급한 호스트에서만 지울 수 있다

5차 · 근본 원인

피카밈의 도메인 구조를 다시 봤다. 프론트엔드는 pick-a-me.me에 배포되어 있고, 백엔드 API는 api.pick-a-me.me에 있다. JWT 쿠키는 백엔드가 발급한다. 즉 api.pick-a-me.me가 심은 쿠키다.

쿠키를 지우는 Set-Cookie: token=; Max-Age=0도 같은 호스트에서 내려와야 한다. 프론트엔드(pick-a-me.me)가 fetch로 /api/auth/logout을 호출해서 받는 응답은 — 브라우저 입장에서는 api.pick-a-me.me가 보낸 것이지만, "크로스 오리진 XHR로 받은 Set-Cookie"라는 제약이 걸린다. domain을 명시하지 않은 쿠키(host-only 쿠키)는 정확히 발급한 호스트에서만 지울 수 있다.

해결책은 프론트가 fetch를 쓰는 대신, 백엔드 호스트로 직접 브라우저 내비게이션을 보내는 것이었다. 백엔드에 GET /auth/logout 엔드포인트를 추가하고, 거기서 쿠키를 삭제한 뒤 프론트로 리다이렉트한다. 브라우저가 직접 이동하면 Same-site 요청이 되고, 쿠키 삭제도 정상 적용된다.

1
프론트가 window.location.href = 'https://api.pick-a-me.me/auth/logout'으로 이동
↓
2
백엔드가 Set-Cookie: token=; Max-Age=0; Path=/ 응답 → 쿠키 삭제됨
↓
3
백엔드가 302 Redirect → https://pick-a-me.me/로 리다이렉트
// 백엔드 — GET /auth/logout @GetMapping("/auth/logout") fun logout(response: HttpServletResponse) { val cookie = Cookie("token", "").apply { maxAge = 0 path = "/" isHttpOnly = true secure = true } response.addCookie(cookie) response.sendRedirect("https://pick-a-me.me/") }

새로고침해도 로그아웃 상태가 유지됐다. 5차 만에 끝났다.

덤 — JSESSIONID가 살아 있었다

쿠키 문제를 해결하고 나니까 또 다른 문제가 보였다. JWT 쿠키를 삭제했는데도 특정 상황에서 인증이 유지됐다. 확인해보니 Spring이 자동으로 생성한 JSESSIONID 세션 쿠키가 있었고, Spring Security가 세션으로도 인증을 처리하고 있었다.

피카밈은 JWT 기반 Stateless 서비스다. 세션이 필요 없다. Spring Security 설정에서 SessionCreationPolicy.STATELESS로 명시하면 Spring은 세션을 생성하지 않고, 세션으로 인증도 시도하지 않는다.

// Spring Security — 세션 생성 안 함 http.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) }

이 설정이 없었던 게 post6에서 다룰 OAuth2 state 문제와도 연결된다. 그쪽은 반대 상황 — "상태가 필요한데 Stateless라서 없는" 경우다.

이 경험에서 배운 것

쿠키는 "심고 지우는 변수"가 아니라 "정책으로 격리된 자원"이다. 발급한 호스트, domain 속성, SameSite, HttpOnly — 이 네 가지가 조합되어 어디서 읽히고 어디서 지워지는지가 결정된다. 로컬에서 됐다고 배포에서 된다는 보장이 없다.

다음 프로젝트에서는 인증 흐름을 배포 환경에서 먼저 검증한다. 로컬과 배포의 도메인 구조가 다르면, 쿠키 동작은 다를 수 있다.
