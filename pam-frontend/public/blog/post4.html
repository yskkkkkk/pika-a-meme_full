사건의 발단

로그아웃 버튼을 누르면 인앱 토스트 알림이 경쾌하게 뜬다. "로그아웃 되었습니다."
안심하고 화면을 새로고침했다. 그런데 귀신같이 내 프로필과 하트 수치가 로그인된 상태 그대로 다시 복원되어 있었다. 1시간 안에 끝날 줄 알았던 이 평범하고 사소한 기능은, 브라우저 보안 정책의 가장 깊은 곳을 관통하며 장장 5차례의 집요한 디버깅 전쟁을 치른 끝에야 완벽한 항복을 받아냈다.

보안 기능은 정상 동작할 때보다 비정상 상황에서 그 실체가 드러난다. 쿠키와 세션, 그리고 토큰은 단순히 넣고 빼는 변수가 아니라 브라우저가 다르게 해석하는 "정책으로 격리된 자원"이었다.

피카밈의 기본 인증 아키텍처는 이렇다. 카카오나 구글 소셜 로그인 성공 시 백엔드가 JWT를 생성해 HttpOnly; Secure; SameSite=Lax 쿠키(`pam_token`)로 클라이언트에 심는다. 브라우저는 다음 API 호출부터 이 쿠키를 자동으로 실어 보낸다. 그렇다면 로그아웃은 단순히 해당 쿠키를 만료(Max-Age=0)시켜 브라우저에서 지워주면 끝나는 문제였다. 적어도 이론상으로는 그랬다.

1차 — React Query 캐시를 의심하다

1차 시도 · 실패

로그아웃 버튼을 눌렀음에도 내 프로필이 살아 있는 것을 보고, 첫 직감은 "React Query의 인메모리 캐시가 stale 상태로 갱신되지 않고 화면에 남아있는 현상"이라 판단했다.

곧바로 로그아웃 핸들러 로직에 queryClient.clear()를 추가했다. 확실히 화면상의 데이터는 그 순간 즉시 사라졌다. 하지만 새로고침을 누르자마자 다시 로그인 정보가 되살아났다. 캐시가 문제가 아니라, 새로고침 시 백엔드로 보내는 `/api/auth/me` 요청에 여전히 유효한 JWT 쿠키가 실려 날아가고 있음이 명백했다. 브라우저 저장소 수준에서 쿠키가 전혀 삭제되지 않았다.

2차 — 크로스 오리진 fetch의 장벽

2차 시도 · 실패

크롬 개발자 도구의 Network 탭을 열어 로그아웃 API 응답 헤더를 추적했다. 백엔드는 분명하게 Set-Cookie: pam_token=; Max-Age=0; Path=/ 헤더를 내려보내고 있었다. 그런데 왜 브라우저는 쿠키를 만료시키지 않고 버젓이 쥐고 있을까?

원인은 브라우저의 **크로스 오리진 요청에 대한 쿠키 적용 차단 정책**이었다. 피카밈 프론트엔드는 pick-a-me.me에, 백엔드 API는 api.pick-a-me.me에 배포되어 있다. JS 코드의 비동기 fetch() 호출은 크로스 오리진 XHR 요청에 해당하므로, 브라우저는 보안상의 이유로 응답 헤더의 Set-Cookie 설정을 가차 없이 무시한다.

물론 credentials: 'include' 옵션을 fetch에 주고 CORS 설정을 허용해주면 해결되는 것처럼 보인다. 그러나 좀 더 확실하고 과하지 않은 해결책을 택했다. 비동기 백그라운드 fetch를 버리고, 로그아웃 버튼을 눌렀을 때 브라우저의 최상단 네비게이션 자체를 백엔드 오리진으로 직접 이동시키는 **탑레벨 GET 네비게이션** 방식을 강제한 것이다.

// [프론트엔드] fetch를 걷어내고 브라우저 네비게이션으로 강제 전환 const handleLogout = () => { // 비동기 fetch 대신 백엔드 오리진으로 직접 페이지 이동 window.location.href = `${API_BASE}/api/auth/logout`; };

이제 브라우저가 직접 페이지를 이동하므로 크로스 오리진 제약 없이 백엔드가 보내는 쿠키 만료 헤더가 깔끔하게 먹히기 시작했다. 로컬 환경에서의 검증은 보기 좋게 성공했다. 하지만 안심하고 운영 서버에 배포한 순간, 버그는 다시 조롱하듯 부활했다.

3차 — 쿠키 domain 불일치의 늪

3차 시도 · 실패

분명 로컬에선 삭제되던 쿠키가 운영 배포 서버에서는 새로고침을 하면 계속 부활했다. 원인을 밝히기 위해 브라우저 Application 탭의 Cookie 저장소를 뒤져보고 엄청난 사실을 발견했다.

브라우저 저장소 내에 동일한 이름을 가졌지만 **domain 속성이 완전히 다른 두 개의 `pam_token` 쿠키**가 나란히 공존하고 있었다. 하나는 배포 전환 과정에서 쿠키 도메인을 지정하기 전에 생성된 `pam_token (domain 없음)`, 다른 하나는 도메인이 명시된 `pam_token (domain=.pick-a-me.me)`.
브라우저는 이름이 같더라도 도메인 속성이 다르면 완전히 별개의 쿠키로 취급한다. 백엔드가 `domain=.pick-a-me.me`를 붙여 만료 헤더를 보냈기 때문에 배포 전 구형 쿠키는 삭제되지 않고 좀비처럼 살아남아 인증을 계속 유효하게 만들었던 것이다.

이를 해결하기 위해 백엔드 로그아웃 핸들러에서 **도메인이 설정된 버전과 설정되지 않은 버전 두 가지 만료 쿠키를 동시에 응답 헤더에 실어보내는 다중 만료 전략**을 취했다.

// [백엔드 AuthController.kt] 두 속성의 쿠키를 동시 삭제 요청 val cookieDomain = ".pick-a-me.me" // 1. domain이 명시되지 않은 구버전 쿠키 만료 response.addHeader("Set-Cookie", "pam_token=; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax") // 2. domain이 명시된 신버전 쿠키 만료 response.addHeader("Set-Cookie", "pam_token=; Domain=$cookieDomain; Path=/; Max-Age=0; HttpOnly; Secure; SameSite=Lax")

도메인 불일치로 인한 좀비 쿠키가 완전히 소멸했다. 드디어 끝난 줄 알았으나, 사파리 브라우저와 일부 크롬 사용자에게서 여전히 새로고침 시 로그인 상태가 풀리지 않는 제보가 잇따랐다.

4차 — Host-Only 쿠키의 주권과 리다이렉트 릴레이

4차 시도 · 실패

이유는 브라우저 쿠키 보안 정책의 가장 핵심인 **Host-Only 쿠키의 강력한 격리 제약** 때문이었다.

백엔드 API 서버(`api.pick-a-me.me`)가 발급한 host-only 쿠키는, 아무리 parent domain인 `.pick-a-me.me`가 만료를 외쳐도 **오직 발급 호스트인 `api.pick-a-me.me` 본인만이 만료시킬 수 있는 절대 주권**을 가진다.
브라우저가 API 통신을 할 때 살아 있는 `api.pick-a-me.me` host-only 쿠키를 함께 전송하므로, 프론트에서 아무리 지우려 애써도 백엔드 필터는 잔존 쿠키를 읽고 로그인을 복원해 버렸다.

결국 프론트엔드와 백엔드가 서로 상대방의 host-only 영역을 침범해 삭제할 수 없다면, **두 오리진을 순차적으로 브라우저가 순회 릴레이 방문하여 각자의 쿠키를 본인 주권 하에 소멸시키는 쿠키 서킷(Circuit)**을 설계할 수밖에 없었다.

🔄 양방향 쿠키 소멸 리다이렉트 서킷

1
유저가 프론트엔드 로그아웃 리다이렉터(pick-a-me.me/api/auth-logout) 진입 ➔ 프론트 Host-Only 및 Parent-Domain 쿠키 만료
↓ 307 Redirect
2
백엔드 로그아웃 엔드포인트(api.pick-a-me.me/api/auth/logout)로 자동 점프 ➔ 백엔드 Host-Only 및 Configured-Domain 쿠키 만료
↓ 302 Redirect
3
프론트엔드 홈(pick-a-me.me/)으로 최종 도달 ➔ 모든 영역의 쿠키가 100% 영구 전멸

양 도메인의 주권 아래 호스트 쿠키를 각각 폭파하고 복귀하는 이 릴레이 서킷 설계로, 드디어 모든 브라우저에서 쿠키 클린 상태를 이뤄냈다. 그러나 귀신을 본 것처럼, 또다시 로그인 정보가 되살아나는 케이스가 발견되었다.

5차 — 잔존하는 JSESSIONID와 Stateless 아키텍처

5차 시도 · 최종 정복 완료

네트워크 트레이스를 해보니 `pam_token`은 단 한 개도 남아 있지 않았다. 완벽하게 쿠키가 비워졌는데 백엔드 `/api/auth/me` API는 여전히 200 OK와 함께 유저 데이터를 반환했다. 이 마법 같은 복원의 실마리는 다름 아닌 **세션 쿠키인 `JSESSIONID`**에 있었다.

소셜 로그인 최초 구현 시 Spring Security OAuth2의 핸드셰이크를 위해 세션 정책을 임시로 SessionCreationPolicy.IF_REQUIRED로 풀어주었던 것이 화근이었다. OAuth2 과정에서 Spring이 내부적으로 임시 세션을 수립하였고, 이 `JSESSIONID` 쿠키가 브라우저에 잔존하여 `pam_token`이 소멸했음에도 세션 ID를 매개로 백엔드가 사용자를 계속 식별 및 인증 처리해주고 있었던 것이다.

피카밈은 완전한 무상태(Stateless) JWT 기반 서비스여야 하므로, 이 모순을 참아 넘길 수 없었다. OAuth2의 CSRF용 `state` 파라미터 보관을 세션 대신 브라우저의 단기 보안 쿠키로 격리하는 CookieOAuth2AuthorizationRequestRepository를 구현 및 장착했다.
그 직후 Spring Security 설정을 엄격한 STATELESS 상태로 전격 환원시켰다.

// [백엔드 SecurityConfig.kt] 임시 세션 발급을 차단하고 쿠키 저장소 장착 http.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) } http.oauth2Login { it.authorizationEndpoint { auth -> // OAuth2 state 파라미터를 임시 세션이 아닌 보안 쿠키에 저장하도록 연결 auth.authorizationRequestRepository(cookieOAuth2AuthorizationRequestRepository) } }

세션의 흔적을 완벽히 지우고, 무상태 아키텍처를 온전히 복구한 순간, 새로고침을 아무리 난타해도 로그인 정보가 부활하는 일은 두 번 다시 발생하지 않았다. 장장 1주일에 걸친 로그아웃의 5중 연쇄 버그가 드디어 완전 정복된 순간이었다.

결론 및 배운 것

💡 이 험난한 여정의 교훈

쿠키와 세션은 단순히 로컬 변수 다루듯 "읽고 지우는 데이터"가 아니다. 브라우저의 주권 영역(Same-Origin), 도메인 격리 레벨, 그리고 프레임워크의 세션 보존 메커니즘이 정교하게 맞물려 작동하는 보안 시스템이다.

개발자 도구에서 로컬(localhost)로 검증하고 만족하는 행위는 반쪽짜리에 불과하다. 호스트가 멀티 서브도메인으로 쪼개지는 운영 인프라의 관점을 고려하여, 설계 단계부터 양방향 보안 주권과 영속성 격리 수준을 엄밀히 따지는 판단력이 진짜 엔지니어의 자질임을 이번 트러블슈팅을 통해 깊이 배웠다.
