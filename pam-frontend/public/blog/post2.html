Pet-Pass 코드의 민낯

Pet-Pass 코드는 솔직히 꽤 지저분했다. 기능이 생기면 그냥 파일 하나 더 만들었다. API 라우트 핸들러 안에 DB 쿼리가 직접 들어있었고, 데이터 가공 로직이 여기저기 중복으로 흩어져 있었다.

문제는 초반엔 전혀 불편하지 않다는 거다. 빠르게 돌아갔고, AI가 코드를 추가하는 것도 편했다. 문제는 수정할 때 생겼다. 뭔가를 바꾸면 예상치 못한 다른 곳이 터졌다. AI도 어디를 고쳐야 할지 문맥을 잃어버리기 시작했다.

코드가 쌓이는 건 눈에 보이지만, 구조가 무너지는 건 다 쌓이고 나서야 보인다.

왜 Clean Architecture인가

픽-아-밈은 Pet-Pass보다 복잡하다. 하트 시스템, 가챠 로직, 이미지 합성, 소셜 로그인, 동시 요청 처리. 이걸 다 한 곳에 쑤셔 넣으면 Pet-Pass보다 훨씬 빠르게 혼돈이 온다.

Clean Architecture를 선택한 이유는 단 하나였다. 비즈니스 로직이 프레임워크에 오염되지 않았으면 했다. JPA를 쓰든 다른 걸 쓰든, Spring이 버전업되든 — 도메인 로직은 건드리지 않아야 한다.

거창하게 들리지만, 실제로는 "어느 폴더에 뭘 넣는지"의 규칙이다.

4계층으로 나누는 방법

Gradle 멀티 모듈로 4개 계층을 물리적으로 분리했다. 의존성 방향이 핵심이다.

pam-api REST Controllers, Security — Delivery Layer
↓ 의존
pam-application UseCase Services, Event Listeners — Application Layer
↓ 의존  |  ↑ 구현
pam-domain Pure Kotlin Entities, Repository Interfaces — Core
↑ 구현 (의존 역전)
pam-infrastructure JPA Adapters, Redis, R2, jOOQ — Implementation Layer

Domain은 아무것도 모른다. Infrastructure는 Domain을 구현할 뿐이다.

중요한 건 pam-domain 모듈이다. 여기엔 순수 Kotlin 객체만 들어간다. JPA 어노테이션도 없고, Spring 의존도 없다. 이 모듈만 떼어내서 단위 테스트해도 돌아간다.

// pam-domain — 순수 Kotlin. @Entity 없음. data class User( val id: UserId, val nickname: String, val provider: OAuthProvider ) { fun validate() { require(nickname.isNotBlank()) { "닉네임은 비어있을 수 없다" } } }

AI에게 계층 규칙을 지키게 하기

계층 구조를 설계하는 것보다 AI가 그 구조를 지키게 하는 게 더 어려웠다.

AI는 빠르게 동작하는 코드를 만드는 데 익숙하다. 레이어가 있어도 "여기다 JPA 어노테이션 달면 되잖아요"라는 식으로 domain 엔티티에 @Entity를 붙이려 했다. 동작은 하지만 원칙이 깨진다.

시도 1 · 실패

AI가 domain 엔티티에 @Entity, @Column을 달기 시작했다. Infrastructure에 있어야 할 JPA 매핑 로직이 domain으로 올라왔다. 코드는 돌아갔지만 계층 분리 의미가 사라졌다.

시도 2 · 부분 성공

계층 규칙을 프롬프트에 명시했다. AI가 지키려 했지만 여전히 application에서 JPA Repository를 직접 주입하는 경우가 생겼다. Domain Interface를 거쳐야 하는 흐름을 놓쳤다.

해결 · AIRULES.md 작성

프로젝트 루트에 AIRULES.md를 만들었다. 계층 의존성 방향, 금지 사항, 도메인 순수성 규칙을 한 문서에 정리해놓고 매 세션마다 참조하게 했다. 규칙이 문서로 고정되니 일관성이 생겼다.

실제로 어떻게 됐나

초반 세팅에 시간이 꽤 걸렸다. 모듈 간 의존성 설정, Flyway DB 형상 관리, GlobalExceptionHandler, 공통 응답 규격 — 기능 코드를 한 줄도 안 짰는데 작업 티켓이 이미 쌓여 있었다.

하지만 그 이후가 달랐다. 하트 시스템을 추가할 때, 밈 생성 로직을 붙일 때 — "이건 Domain에", "이건 Infrastructure에"가 자연스럽게 정해졌다. AI도 구조를 파악하고 나니까 헷갈리지 않았다. AIRULES.md가 AI의 단기 기억을 대신해주는 역할을 했다.

이 경험에서 배운 것

AI에게 코드 스타일보다 구조 규칙을 먼저 가르쳐야 한다. 코드는 AI가 금방 짜지만, 구조는 한 번 무너지면 되돌리기 어렵다.

AIRULES.md처럼 규칙을 명문화해두면 AI뿐 아니라 나 자신도 흔들리지 않는다. 설계 의도를 문서로 남기는 것 자체가 프로젝트 자산이다.
