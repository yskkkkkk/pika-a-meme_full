다시 안 할 것 ① — 기술 스택 결정을 뒤로 미루기

Canvas 에디터를 처음에 만들었다가 나중에 CSS 말풍선 방식으로 전환했다. R2 업로드 로직을 전부 구현했다가 삭제하고 JSONB composition 방식으로 전환했다. 두 경우 모두 "일단 구현하고 보자"는 접근 때문에 발생한 낭비다.

렌더링 방식과 저장 전략은 서비스의 핵심 아키텍처 결정이다. 이걸 POC 없이 구현부터 시작했던 것이 문제였다. 5줄짜리 프로토타입을 먼저 만들고, 그 결과물이 요구사항을 충족하는지 확인한 다음 본 구현으로 가는 순서가 맞다.

구현을 많이 할수록 방향 전환 비용이 커진다. 확신이 없는 결정은 최소한의 코드로 검증을 먼저 해야 한다.

다시 안 할 것 ② — 프레임워크 기본 동작 모른 채 설정하기

OAuth2 state 소실 버그는 SessionCreationPolicy.STATELESS가 Spring Security OAuth2의 기본 가정을 깬다는 사실을 모른 채 설정해서 생겼다. 해결하려고 IF_REQUIRED로 변경했다가 이번엔 JSESSIONID가 남아서 로그아웃이 깨졌다.

프레임워크의 기본값에는 이유가 있다. 그 이유를 이해하지 않고 설정을 바꾸면, 바꾼 설정이 다른 곳과 충돌할 때 원인을 찾기 어려워진다. Spring Security를 쓸 때는 필터 체인의 각 필터가 무엇을 하는지, 세션 정책이 어디에 영향을 미치는지를 먼저 파악했어야 했다.

다시 안 할 것 ③ — 새 기능 완성 후 접점 검증 생략하기

미션 시스템을 완성하고 배포한 직후 버그 4개가 연달아 나왔다. 전부 MissionService 내부가 아니라 바깥에서 터진 문제들이었다. API 레이어의 인증 가드, 프론트의 잔액 체크, HeartService의 실행 순서.

새 기능을 배포하기 전에 체크해야 할 것은 기능 내부만이 아니다. 그 기능이 기존 시스템과 어떻게 연결되는지, 호출 방향과 의존 방향 양쪽의 경계 조건을 함께 점검해야 한다. 다음 프로젝트에서는 새 기능 배포 전 "접점 체크리스트"를 별도로 만들 것이다.

다시 안 할 것 ④ — 비용이 발생하는 엔드포인트 무방비로 두기

Cloudflare가 있으면 DDoS는 막힌다. 하지만 비용 폭탄을 만드는 건 규모가 아니라 빈도다. 분당 수십 회의 반복 요청이 Neon 연산 쿼터를 소진하고 Upstash 명령 수 요금을 발생시킨다.

Rate Limiting은 처음부터 설계에 포함됐어야 했다. 뽑기 엔드포인트에 Rate Limit이 없는 상태로 배포했을 때, 만약 의도적인 반복 요청이 들어왔다면 비용 알람이 먼저 왔을 것이다. 외부 API 호출이나 DB 쿼리가 발생하는 엔드포인트는 서비스 초기부터 제한을 걸어야 한다.

다시 안 할 것 ⑤ — 마이그레이션 버전을 부주의하게 관리하기

V10 버전 충돌이 생겼다. 서로 다른 브랜치에서 독립적으로 V10 파일을 만들었고, 머지됐을 때 Flyway가 두 파일을 모두 발견해서 에러가 났다. Flyway는 같은 버전 번호의 파일이 두 개 있으면 실행을 중단한다.

혼자 작업해도 브랜치가 여러 개면 버전 충돌이 생긴다. 다음 마이그레이션 버전을 정할 때는 이미 존재하는 파일 목록을 먼저 확인하는 것을 습관으로 만들어야 한다. 또는 타임스탬프 기반 버전(V20260514120000__)을 쓰는 것도 충돌 방지에 효과적이다.

AI 협업의 솔직한 회고

피카밈은 AI와 함께 만든 프로젝트다. AIRULES.md를 만들고, 계층 규칙을 AI에게 명시적으로 알려줬다. 1개월을 함께 작업한 뒤 정직하게 평가하면 이렇다.

AI가 잘한 것: 보일러플레이트 코드, Flyway 마이그레이션, JPA 어댑터, API 레이어 CRUD. 패턴이 명확한 작업은 빠르고 정확하다. AIRULES.md로 계층 규칙을 알려주자 Clean Architecture 경계를 대체로 지켰다.

AI가 못한 것: Spring Security의 미묘한 설정 조합. 기존 코드와 새 기능의 접점에서 생기는 버그. "이 결정의 나비 효과가 어디까지 갈 것인가"에 대한 판단. 이런 문제는 AI가 일관되게 놓쳤다.

AI는 코드를 빠르게 만들지만, 코드가 시스템 안에서 어떻게 작동하는지는 개발자가 이해해야 한다. AI가 만든 코드를 이해하지 못한 채 "그냥 작동하면 됐지"로 넘어가면, 나중에 그 코드가 어디서 터질지 예측할 수 없다.

AIRULES.md는 효과가 있었다. "UseCase 인터페이스는 application 레이어에만 있어야 한다", "도메인 레이어는 외부 의존성을 갖지 않는다"를 명시해두자 AI가 이 규칙을 지키는 쪽으로 코드를 생성했다. 규칙을 코드 주석이나 README에 묻어두는 것보다, AI가 매 세션마다 읽을 수 있는 별도 파일로 분리하는 것이 효과적이었다.

다음 프로젝트의 화두

피카밈을 만들면서 해결하지 못한 것들, 그리고 다음에 더 잘하고 싶은 것들이 있다.

테스트: MissionService의 단위 테스트는 있지만 통합 테스트가 부족했다. 접점 버그 4개 중 2개는 통합 테스트가 있었다면 배포 전에 잡혔을 문제들이다. 다음 프로젝트는 통합 테스트 전략을 처음부터 잡고 시작할 것이다.

관찰성(Observability): 로그는 있지만 메트릭과 트레이싱이 없다. "현재 뽑기가 얼마나 자주 일어나고 있는가", "평균 응답 시간은 얼마인가"를 실시간으로 보는 방법이 없다. Sentry와 분석 로깅이 미완 항목으로 남아 있는 이유다.

AI 협업 방식: AIRULES.md는 계층 규칙을 지키게 하는 데 효과적이었다. 다음 단계는 "이 API의 사용 시나리오"를 AI에게 알려주는 방법을 찾는 것이다. 접점 버그는 결국 AI가 "이 코드를 호출하는 쪽이 어떤 전제를 가지고 있는지"를 모르기 때문에 생겼다.

이 프로젝트에서 가져가는 것

백엔드 개발자가 프론트엔드까지 직접 짜봐야 하는 이유를 알게 됐다. CORS 정책이 쿠키 삭제에 미치는 영향, 브라우저가 Set-Cookie를 처리하는 방식, 네비게이션과 fetch의 차이 — 이것들은 백엔드에서 API만 만들었다면 알 수 없었던 것들이다. 풀스택 경험이 "왜 이 API가 이렇게 설계되어야 하는지"를 이해하는 데 직접적인 영향을 미쳤다.

그리고 기술 부채는 느리게 쌓인다. 매 결정마다 "지금 당장 작동하는 코드"와 "나중에 고치기 어려운 구조" 중 하나를 선택하게 된다. 피카밈에서는 몇 번 잘못된 선택을 했고, 그 대가를 나중에 디버깅 시간으로 치렀다. 다음 프로젝트에서 그 시간을 줄이는 것이 목표다.
