왜 이관해야 했나

어느 날 Railway 대시보드를 보니 이런 메시지가 떠 있었어요.

"9 days or $2.77 left"

무료 크레딧이 바닥을 드러내고 있었거든요. Railway는 처음 프로젝트를 시작할 때 에이전트들이 가장 먼저 추천한 플랫폼이었어요. 이유는 단순했거든요. GitHub 레포를 연결하고 브랜치를 지정하면 끝. pam-backend/** 경로에 변경이 감지되면 알아서 Docker 빌드하고 배포합니다. 대시보드에서 환경변수 입력하고, 로그 보고, 롤백하고. 개발에만 집중할 수 있는 구조였어요.

그런데 무료는 영원하지 않거든요. 크레딧이 소진되면 과금이 시작됩니다. 포트폴리오 프로젝트에 매달 돈을 내는 건 부담이고요. 그래서 무료로 쓸 수 있는 OCI(Oracle Cloud Infrastructure) Free Tier로 이관하기로 했어요.

이 결정 이전에 소스 안에 이미 이관 계획이 기록되어 있었거든요.

백엔드 서버 OCI(Oracle Cloud) 이관 준비

현재 Railway Docker 운영 중. OCI로 이관을 위한 사전 준비: (1) OCI 인스턴스 스펙/구성 검토. (2) Docker Compose 또는 OCI Container Instance 배포 방식 결정. (3) 도메인/Cloudflare 연결 변경 계획. CI/CD GitHub Actions 수정 범위 포함.

백로그에 박아두고 "언젠가"로 미뤄두던 태스크가 "지금 당장"이 된 거예요.

OCI 인스턴스 준비

OCI Free Tier의 핵심은 VM.Standard.A1.Flex예요. ARM 기반 Ampere 프로세서로, Free Tier에서 최대 4 OCPU + 24GB RAM까지 쓸 수 있거든요. 1 OCPU당 6GB RAM 비율로 배분됩니다.

그런데 실제로 만들어보니 벽이 있더라고요. 서울/춘천 리전의 A1.Flex 용량이 꽉 찬 상태였거든요. 6GB 인스턴스를 만들려고 수 시간 동안 시도했지만 계속 "용량 부족" 응답이 돌아왔어요. 결국 1GB RAM으로 타협해서 인스턴스를 생성했습니다.

Phase 1 — OOM 방어전: 38분의 사투

서버에 Docker와 Git을 설치하고 레포를 클론한 뒤 docker build를 실행했어요. 그리고 서버가 뻗었습니다.

Kotlin + Gradle 빌드는 JVM을 띄우고 컴파일러 데몬을 올리거든요. 1GB RAM에서는 이것만으로도 한계를 넘더라고요. OOM(Out of Memory) 킬러가 프로세스를 강제로 죽였습니다.

해결책은 스왑 메모리 4GB 강제 주입이었어요.

sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

하드디스크 공간을 RAM처럼 쓰는 방식이거든요. 물리 RAM 1GB + 스왑 4GB = 가용 메모리 5GB. 속도는 느리지만 최소한 죽지는 않더라고요.

이 상태로 빌드를 재시도했어요. Kotlin 컴파일러 데몬이 뻗는 악조건에서도 플랜 B 모드(데몬 없이 직접 컴파일)로 끈질기게 버텨냈습니다.

Phase 3 — 이중 방화벽 개방

8080 포트로 귀를 열었는데 외부에서 접근이 안 되더라고요. OCI는 네트워크 보안이 이중으로 걸려 있거든요.

1층: OCI VCN Security List — 클라우드 레벨의 방화벽. 인스턴스에 도달하기 전에 차단합니다.
2층: Ubuntu iptables — OS 레벨의 방화벽. 패킷이 OS에 도착해도 여기서 막히고요.

두 곳 모두 열어야 합니다.

OCI 콘솔에서 Ingress Rules 추가:

Source CIDRProtocolPort용도
0.0.0.0/0TCP22SSH
0.0.0.0/0TCP8080백엔드 (임시)

Ubuntu iptables:

sudo iptables -I INPUT 1 -p tcp --dport 8080 -j ACCEPT
sudo netfilter-persistent save

이제 외부에서 8080 포트로 접근이 됩니다.

Phase 4 — Nginx + SSL + Cloudflare Full Strict

Cloudflare DNS에서 api.pick-a-me.me를 OCI IP로 연결했어요. CNAME으로 Railway 주소를 가리키던 것을 A 레코드로 바꿨고요.

그런데 Error 522가 떴어요. Cloudflare Proxied 모드는 오리진에 80/443 포트로 접속하는데, 백엔드는 8080에서만 듣고 있었거든요.

Nginx를 리버스 프록시로 세웠습니다.

sudo apt install -y nginx
# /etc/nginx/sites-available/pam-backend
server {
    listen 80;
    server_name api.pick-a-me.me;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header CF-Connecting-IP $http_cf_connecting_ip;
    }
}

CF-Connecting-IP 헤더를 명시적으로 전달한 게 핵심이에요. Cloudflare가 실제 클라이언트 IP를 이 헤더에 담아 보내는데, Nginx가 이걸 Spring Boot까지 흘려보내야 Rate Limiting이 제대로 동작하거든요.

그다음 SSL 인증서를 발급했어요.

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d api.pick-a-me.me

Certbot이 자동으로 Nginx 설정을 수정하고 Let's Encrypt 인증서를 발급해 바인딩했어요. 90일마다 자동 갱신되고요.

Cloudflare SSL/TLS 모드를 Full → Full (Strict)로 전환했습니다.

모드클라이언트 → CFCF → 오리진인증서 검증
FlexibleHTTPSHTTP (평문)없음
FullHTTPSHTTPS없음 (자체서명 허용)
Full (Strict)HTTPSHTTPS유효한 인증서 필수

Full (Strict)에서 다시 헬스체크입니다.

curl https://api.pick-a-me.me/actuator/health
→ {"status":"UP"}

클라이언트부터 Cloudflare, Nginx, Spring Boot까지 전 구간 암호화 완료입니다.

Phase 5 — GitHub Actions CI/CD 혁신

Railway를 쓸 때는 대시보드에서 GitHub 연동으로 배포 자동화를 설정했어요. pam-backend/**에 변경이 생기면 Railway가 알아서 빌드하고 배포했고요. 코드 한 줄도 쓸 필요가 없었거든요.

OCI로 오면 이걸 직접 만들어야 합니다. 처음 설계는 "SSH로 서버에 접속해서 git pull 후 docker build"였어요. 실제로 그렇게 동작하는 GitHub Actions 워크플로우를 먼저 만들었고요.

그런데 문제가 있더라고요. 배포할 때마다 서버에서 38분짜리 빌드가 돌아간다는 거예요. 1GB RAM 서버가 매 배포마다 한계치를 넘어서거든요. 서비스가 죽을 수도 있고요.

해결책은 GHCR(GitHub Container Registry) + SSH Pull 방식이었어요.

🔴 기존: SSH + 서버 빌드

  • main push
  • OCI 서버에 SSH 접속
  • git pull
  • docker build (38분)
  • docker run

🟢 변경: GHCR + SSH Pull

  • main push
  • GitHub Actions에서 빌드 (2분)
  • GHCR에 이미지 push
  • OCI 서버: docker pull + run만
  • 서버 부하 0

GitHub Actions는 고사양 서버(ubuntu-latest)에서 무료로 빌드해주거든요. OCI 서버가 해야 할 일은 완성된 이미지를 받아서 실행하는 것뿐이고요.

워크플로우 구조는 이렇습니다.

# .github/workflows/deploy-backend.yml
on:
  push:
    branches: [main]
    paths: ['pam-backend/**']

jobs:
  build-and-push:     # GitHub Actions에서 빌드 → GHCR push
  deploy:             # OCI 서버에 SSH → pull + restart
    needs: build-and-push

결과는 이렇습니다.

Phase 6 — 보안 마무리: Cloudflare WAF 우회 차단

서버가 살아있고 HTTPS도 됩니다. 그런데 한 가지 구멍이 남아 있더라고요. OCI Security List에서 80/443이 0.0.0.0/0으로 열려 있어, 서버 IP를 직접 치면 Cloudflare WAF를 완전히 우회할 수 있었거든요.

코드 레벨에서 처리한 것들

서버 세팅만 하면 끝이 아니더라고요. 소스 코드에도 이관에 맞게 바꿔야 할 것들이 있었거든요. 사실 이건 이미 docs/known-issues.md에 기록해뒀던 항목이었어요.

known-issues.md · SECURITY-01 P2
RateLimitFilter — useForwardedHeaders 전환

⏳ OCI 이관 시 | OCI+Nginx 구성 확정 후 CF-Connecting-IP 전용으로 수정 필요. 현재 false이므로 안전.

Nginx 구성이 완료됐으니 이제 이 항목을 해소할 수 있어요.

application.yml 변경:

# 변경 전
use-forwarded-headers: ${RATE_LIMIT_USE_FORWARDED_HEADERS:false}

# 변경 후
use-forwarded-headers: ${RATE_LIMIT_USE_FORWARDED_HEADERS:true}

RateLimitFilter.kt의 IP 추출 로직은 이미 잘 만들어져 있었어요.

private fun clientIp(request: HttpServletRequest): String {
    if (properties.useForwardedHeaders) {
        // CF-Connecting-IP 우선 (위조 불가)
        request.getHeader("CF-Connecting-IP")
            ?.takeIf { it.isNotBlank() }
            ?.let { return it.trim() }

        // X-Forwarded-For 폴백
        request.getHeader("X-Forwarded-For")
            ?.split(",")?.firstOrNull()?.trim()
            ?.takeIf { it.isNotBlank() }
            ?.let { return it }
    }
    return request.remoteAddr ?: "unknown"
}

CF-Connecting-IP를 먼저 보고, 없으면 X-Forwarded-For로 폴백합니다. Cloudflare가 항상 CF-Connecting-IP를 설정하므로, 클라이언트가 X-Forwarded-For를 위조해도 영향이 없고요.

그 외에 README.md, ENV.md, docs/runbook.md의 Railway 관련 내용도 전부 OCI 기준으로 업데이트했어요. 롤백 절차도 "Railway 대시보드에서 Redeploy"에서 "GitHub Actions Re-run 또는 이전 GHCR 이미지 태그로 재실행"으로 바꿨고요.

Railway는 진짜 편했어요

이관을 마치고 나서 느낀 가장 솔직한 감상은 이거예요.

Railway는 진짜 편하더라고요. 유료인 맛이 있어요. 에이전트들이 초반에 추천했던 이유가 있었거든요.

OCI 이관을 하면서 제가 직접 해야 했던 것들을 나열해보면 이렇습니다.

  • 스왑 메모리 설정
  • Docker 설치 및 빌드
  • OCI Security List 방화벽 규칙 34개 수동 입력
  • Ubuntu iptables 설정
  • Nginx 설치 및 리버스 프록시 설정
  • Let's Encrypt 인증서 발급
  • Cloudflare DNS 레코드 변경 (CNAME → A 레코드)
  • Cloudflare SSL 모드 조정 (Flexible → Full Strict)
  • GitHub Actions 워크플로우 작성 (GHCR 빌드 + SSH Deploy)
  • GitHub Secrets 등록 (OCI_HOST, OCI_USER, OCI_SSH_PRIVATE_KEY)
  • 코드 변경 (use-forwarded-headers, 문서 업데이트)

Railway를 쓸 때는 이 중 대부분을 대시보드 클릭 몇 번으로 해결했어요. GitHub 레포 연결, 환경변수 입력, 커스텀 도메인 추가. 그게 전부였거든요.

물론 Railway도 완벽하지는 않아요. 무료 크레딧이 소진되면 과금되고요. 하지만 그 편의성에는 분명히 그만한 값어치가 있더라고요. 처음 프로젝트를 시작하거나, 빠르게 배포하고 개발에 집중해야 할 때는 Railway 같은 PaaS가 훨씬 합리적인 선택이에요.

OCI Free Tier는 공짜라는 강점이 있어요. 다만 그 공짜의 대가로 설정에 쏟은 시간과 노력이 있고요. 어느 쪽이 낫냐는 프로젝트 상황에 따라 다르더라고요.

이 경험에서 가져가는 것

PaaS와 IaaS의 차이를 몸으로 느꼈어요. PaaS는 편의성을 팔고, IaaS는 제어권을 팔더라고요. 둘 다 장단점이 있어서, 상황에 따라 선택이 갈리고요.

1GB짜리 공짜 서버에서 버티는 법도 이번에 배웠어요. 스왑 메모리, 빌드 분리, CI 서버 활용 — 제약이 있으니까 오히려 이런 우회로를 찾게 되더라고요.

그리고 보안은 한 겹으로 끝나지 않더라고요. Cloudflare WAF만 믿고 있다가 서버 IP 직접 호출이라는 구멍을 봤거든요. OCI Security List, iptables, Nginx, 애플리케이션 레이어 Rate Limiting까지 겹쳐두고 나서야 마음이 좀 놓였습니다. 다음엔 이 겹을 처음부터 깔고 시작하기로...
