처음 설계는 단순했다

밈을 뽑으면 이미지가 완성된다. 완성된 이미지는 저장해야 한다. 이게 처음 생각이었다.

Cloudflare R2에 S3 호환 SDK로 업로드하는 어댑터를 짰다. 밈 뽑기 유스케이스 흐름은 이랬다. 이미지와 문구를 조합하고, 완성된 결과물을 R2에 올리고, 그 URL을 DB에 기록한다. TASK-260429-19가 완료 처리됐다. 그런데 뭔가 계속 걸렸다.

// 초기 설계 — 뽑기마다 R2에 합성 이미지 업로드 val image = imageRepo.findRandom() val phrase = phraseRepo.findRandom() val composedUrl = r2Storage.upload(renderMeme(image, phrase)) // R2 PUT val userMeme = UserMeme(imageUrl = composedUrl, ...) userMemeRepo.save(userMeme) // DB INSERT

고아 파일이라는 유령

R2 업로드가 성공한 직후 DB 저장이 실패하면 어떻게 되는가.

R2에는 이미지가 있다. DB에는 레코드가 없다. 이 이미지는 누구의 것인가. 어떻게 지울 수 있는가. 트랜잭션 안에 R2 업로드를 넣을 수 없다 — R2는 외부 HTTP 호출이고, 롤백이 없다.

해결책은 보상 트랜잭션이었다. DB 저장 실패 시 R2에 올라간 파일을 다시 삭제하는 로직을 만든다. 하지만 보상 트랜잭션도 실패할 수 있다. 그러면 정리 배치가 필요하다. 정리 배치가 실수로 살아 있는 파일을 지우면 감사 로그가 필요하다.

고아 파일 하나를 해결하려다 시스템이 불어나고 있었다. TASK-260501-01을 열었다가, 멈췄다. 이게 진짜 필요한 복잡성인지를 먼저 물어야 했다.

외부 시스템 호출은 트랜잭션 경계 밖에 있다. DB는 롤백할 수 있어도 R2는 롤백할 수 없다.

사용자에게 필요한 건 이미지가 아니었다

요구사항으로 돌아갔다. 사용자가 실제로 하는 행동은 세 가지다. 밈을 뽑는다. 결과 카드를 본다. 마음에 들면 저장하거나 공유한다.

"결과 카드를 다시 본다"는 건 무슨 뜻인가. 이미 만들어진 이미지 파일이 필요한 게 아니다. 그 카드를 똑같이 다시 그릴 수 있으면 된다. 이미지가 아니라 재현에 필요한 재료가 필요한 것이다.

재료는 세 가지다. 어떤 동물 이미지를 썼는가, 말풍선 위치가 어디였는가, 문구가 무엇이었는가. 이 셋을 저장하면 언제든 동일한 카드를 다시 렌더링할 수 있다. 그리고 소스 이미지(동물 사진)는 이미 R2에 있다 — 재사용하면 된다.

JSONB 한 컬럼으로

R2 업로드 코드를 전부 지웠다. user_memes.composition JSONB 컬럼 하나가 그 자리를 대신했다.

// 새 설계 — 재현 재료만 JSONB로 저장 data class MemeComposition( val imageUrl: String, // 소스 이미지 URL (img.pick-a-me.me) val subjectPosition: String, // 말풍선 위치 (TOP_LEFT 등) val phraseText: String // 문구 텍스트 스냅샷 )

DB 저장이 실패하면 아무것도 남지 않는다. 고아 파일이 없다. 보상 트랜잭션도 없고, 정리 배치도 없다. 아무것도 지울 게 없으니까.

이전 — 뽑기마다 R2 업로드
저장 대상합성된 결과 이미지 파일
고아 파일DB 저장 실패 시 R2에 잔존
복구 방법보상 트랜잭션 + 정리 배치
뽑기 비용R2 PUT 요청 매번
이후 — JSONB 재료 저장
저장 대상재현 재료 3개 (JSONB)
고아 파일구조상 발생 불가
복구 방법필요 없음
뽑기 비용DB 쓰기 1회

트레이드오프

이 결정의 약점은 두 가지다.

첫째, 이미지 다운로드가 클라이언트 렌더링이다. html2canvas가 브라우저에서 카드를 그려 저장한다. 폰트 로딩 타이밍에 따라 결과물에 차이가 생길 수 있고, 서버에서 완성 이미지를 만들어 내려주는 방식보다 품질 제어가 어렵다. 지금은 허용 가능한 수준이라고 판단했다.

둘째, 소스 이미지가 R2에서 삭제되면 카드를 재현할 수 없다. 소스 이미지 URL이 SSOT다. 이건 운영상 소스 이미지를 함부로 지우지 않는 것으로 해결한다 — 지금 규모에서 이미지 수백 장의 보관 비용은 사실상 0에 가깝다.

그럼 OG 이미지는?

링크를 카카오톡에 붙여넣으면 미리보기 이미지가 떠야 한다. SNS 크롤러는 JavaScript를 실행하지 않으므로 서버사이드 HTML에 <meta property="og:image">가 있어야 한다. 클라이언트 렌더링으로는 해결이 안 된다.

여기서 다시 R2가 필요해 보인다. 그런데 뽑기할 때마다 모든 결과를 R2에 올릴 이유는 없다. 실제로 공유하는 사람만, 공유하는 그 순간에만 올리면 된다.

1
공유하기 클릭 — og_image_url이 이미 있으면 바로 공유 URL 전달
2
없으면 — 클라이언트에서 카드 캡처 → POST /api/memes/{id}/og-image
3
백엔드 — R2 og/{memeId}.png 업로드 → og_image_url 저장 → URL 반환
4
/share/{memeId} — generateMetadata()에서 SSR로 OG 태그 주입

결과를 보고 버리는 사용자에게는 R2 비용이 발생하지 않는다. 공유 의사가 생긴 사람에게만, 그 시점에만 비용이 발생한다. 뽑기마다 전부 저장하던 초기 설계와 비교하면 같은 기능을 훨씬 적은 비용으로 구현한다.

이 흐름은 아직 구현 전이다. html2canvas를 html-to-image로 교체하는 작업이 선행되어야 한다. 하지만 설계는 확정됐고, "모든 결과를 R2에 저장하지 않는다"는 결정과 충돌하지 않는다.

이 결정에서 배운 것

처음 설계는 "필요할지 모른다"는 가정 위에 쌓이기 쉽다. "지금 필요한가"를 먼저 물어야 한다. 아니라면 git이 기억하게 두면 된다.

그리고 정말 필요해졌을 때도 처음부터 전부 저장할 필요는 없다. 비용이 발생하는 시점을 늦출 수 있다면 — 실제 필요가 발생한 그 순간으로 미루는 것이 더 나은 설계일 수 있다.
