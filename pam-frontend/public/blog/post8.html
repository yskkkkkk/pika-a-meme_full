미션 시스템 완성

미션 시스템은 피카밈의 스페셜 하트 공급 루트다. 출석 체크, 연속 방문, 첫 공유, 주간 공유, 보관함 10개 · 30개 달성, 숨겨진 테마 발견. 각 미션을 달성하면 SPECIAL 하트가 지급된다.

MissionService를 완성했을 때 내부 로직은 깔끔했다. trigger() 하나로 모든 진입점을 받고, 중복 지급 방지, 주간/일간 period 키, streak 추적까지 테스트를 거쳐서 작동했다.

배포 직후 점검 중에 버그 4개가 연달아 나왔다. 전부 MissionService 바깥에서 터진 문제들이었다.

버그 ① — 비로그인 유저도 SPECIAL 뽑기가 됐다

증상
로그인하지 않은 상태에서 heartType=SPECIAL로 뽑기 API를 직접 호출하면 400/401이 아닌 200이 반환됐다.
원인
SPECIAL 하트는 로그인 전용이다. 그런데 MemeController에서 heartType이 SPECIAL일 때 userId가 null인 경우를 차단하는 가드가 없었다.
Before
After
fun compose( @AuthUser userId: UUID?, heartType: HeartType ): ResponseEntity<*> { // 인증 가드 없음 return service.compose( userId, heartType ) }
fun compose( @AuthUser userId: UUID?, heartType: HeartType ): ResponseEntity<*> { if (userId == null && heartType == SPECIAL) return unauthorized() return service.compose( userId, heartType ) }

SPECIAL 하트를 지급하는 로직은 MissionService에서 정확하게 작동했다. 소비하는 로직은 HeartService에서 잔액을 확인했다. 그런데 API 진입 직전에 "SPECIAL은 로그인 필수"라는 규칙을 강제하는 코드가 없었다.

버그 ② — 하트가 없어도 뽑기 진입이 됐다

증상
스페셜 하트가 0개인 상태에서도 UI상 뽑기 버튼이 활성화되어 눌렸다. 백엔드에서 잔액 부족으로 오류가 반환되지만 UX가 깨졌다.
원인
프론트엔드 page.tsx의 executeSpecialDraw() 함수가 진입 전에 잔액을 확인하지 않았다. 잔액 체크는 API 호출 이후 오류 응답에서만 이루어졌다.
Before
After
async function executeSpecialDraw() { // 잔액 체크 없음 await drawMeme( { heartType: 'SPECIAL' } ) }
async function executeSpecialDraw() { if (special.count <= 0) { showInsufficientToast() return } await drawMeme( { heartType: 'SPECIAL' } ) }

백엔드는 잔액이 없으면 오류를 반환한다. 그러나 사용자 경험 관점에서 잔액 체크는 UI 레이어에서 먼저 이루어져야 한다. 서버 왕복 없이 즉시 피드백을 주는 것이 맞다.

버그 ③ — 충전량이 항상 0으로 기록됐다

증상
미션 달성 시 SPECIAL 하트가 정상 지급됐지만, DB의 HeartHistory에 기록된 chargedAmount가 항상 0이었다.
원인
beforeCount를 캡처하는 시점이 문제였다. chargeIfNeeded()를 먼저 호출하고 나서 beforeCount를 캡처했기 때문에, 이미 충전된 이후의 값이 "충전 전 값"으로 기록됐다.
Before — 순서가 뒤집힌 코드
After — 충전 전에 캡처
fun grantSpecialHeart( userId: UUID, amount: Int ) { chargeIfNeeded(userId, amount) val beforeCount = // 이미 충전됨 getCount(userId) recordHistory( userId, beforeCount, amount ) }
fun grantSpecialHeart( userId: UUID, amount: Int ) { val preChargeCount = getCount(userId) // 충전 전 chargeIfNeeded(userId, amount) recordHistory( userId, preChargeCount, amount ) }

chargedAmount = currentCount - beforeCount. beforeCount를 충전 이후에 읽으면 둘의 차이는 항상 0이다. 코드가 틀린 게 아니라 실행 순서가 틀렸다.

버그 ④ — 미사용 변수

③을 수정하는 과정에서 이전 코드에서 사용하던 charged 변수가 리팩토링 후 아무 데서도 참조되지 않는 채 남아 있었다. 컴파일 경고가 발생했다. 변수 제거로 해결했다.

규모는 가장 작지만 ③을 고칠 때 놓쳤으면 정적 분석 경고가 쌓였을 문제다.

4개 버그의 공통점

MissionService 내부 로직은 올바르게 작동했다. 버그들은 전부 미션 시스템이 기존 시스템과 만나는 접점에서 발생했다.

① — MemeController: API 레이어에서 심어야 할 인증 가드 누락
② — page.tsx: 프론트 UI 레이어에서 잔액 사전 확인 누락
③ — HeartService: 기존 메서드에 로직 추가 시 실행 순서 오류
④ — HeartService: 리팩토링 후 정리되지 않은 잔재

새 기능 자체가 아니라, 새 기능이 기존 코드와 연결되는 접점이 버그의 진원지였다. MissionService를 아무리 정교하게 짜도, 그것을 호출하는 쪽과 그것이 의존하는 쪽의 계약이 맞지 않으면 시스템은 깨진다.

이 경험에서 배운 것

새 기능을 완성한 후 테스트는 그 기능 내부만 검증하기 쉽다. 그런데 버그는 새 기능과 기존 시스템의 경계, 즉 호출 방향과 의존 방향 양쪽에서 함께 터진다.

미션 시스템을 배포한 뒤 가장 먼저 체크했어야 했던 것은 "미션이 정상 달성되는가"가 아니라 "SPECIAL 뽑기 진입 경로 전체가 올바르게 통제되는가"였다. 기능 경계 밖의 흐름을 함께 점검하는 습관이 접점 버그를 줄인다.
